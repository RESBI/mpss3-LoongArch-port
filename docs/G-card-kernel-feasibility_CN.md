# 附录 G　给 KNC 卡换一个更新的内核：可行性调研

　　本报告正文讲的都是**主机侧**。这一节回答另一个问题：**能不能给卡本身编一个比 2.6.38.8 更新的 Linux 内核。** 结论先给：「技术上说得通，实践上是一个专门项目，且不建议作为第一步」——理由与依据如下。

---

## G.1　k1om 的真实身份

　　k1om 不是一套独立架构，而是 `arch/x86` 里的一个**处理器族**。这不是推测，是 Intel 自己树里的写法：

| 事实 | 出处 |
|---|---|
| `k1om` 走 x86 的源码目录 | 卡端内核树顶层 `Makefile` 的 `ifeq ($(ARCH),k1om)` 分支把 `SRCARCH` 设为 `x86` |
| 编译器前缀 | `arch/x86/Makefile` 里 `x86_64-k1om` |
| 独立的 ELF 机器类型 | `include/linux/elf-em.h:36` 起，`EM_L1OM` 180、`EM_K1OM` 181 |
| 处理器族配置符号 | `arch/x86/Kconfig.cpu:290` 的 `config MK1OM` |
| 平台配置符号 | `arch/x86/Kconfig:348` 的 `config X86_MICPCI`，它 `select MK1OM` |

　　而 `arch/x86/Kconfig.cpu` 里 `MK1OM` 的自述说得更清楚，值得原样记下：这颗处理器是顺序四线程设计，**与 x86-64 大体兼容但向量单元不同**，这些差异**迫使调用约定不兼容**，于是 GCC 与 binutils 给它分配了独立的 ELF 机器类型；并且明确写道，Intel 之后的产品会留在 x86 生态里，**不会是这条不兼容分支的后代**。

　　**这条「调用约定不兼容」是整个附录的关键**：`EM_K1OM` 从未出现在上游内核里，所以上游内核连执行一个 k1om 用户态程序都做不到。

## G.2　上游主线对 MIC 家族做过什么

　　把时间线摆出来，才能判断「换新内核」意味着什么：

| 版本 | 事件 |
|---|---|
| 3.13 | `drivers/misc/mic/` 进入主线（宿主驱动与卡端驱动两个提交，2013 年 9 月，Greg Kroah-Hartman 收） |
| 4.3 到 4.6 | SCIF 总线、COSM、VOP（virtio over PCIe）陆续加入 |
| **5.10** | **整个 MIC 驱动族被删除**，提交理由一句话：「相关设备已经停产」。删掉 66 个文件、约两万一千行，含 `include/linux/scif.h`、`samples/mic/mpssd/` 与 `Documentation/misc-devices/mic/` |
| 2022 | **binutils 删除 k1om 与 l1om**：`bfd/cpu-k1om.c`、`k1om_elf64_vec` 等一并去掉 |

　　有一处容易误判，必须点明：**主线里那个 `drivers/misc/mic/card/` 并不是这块卡上跑的东西。** 它的 `module_init` 硬检查 CPU 签名是「family 11、model 1」，那是 **VASP／SDV 模拟器**的标识；真实 KNC 硅片是「family 6、model 11」，Intel 树外的生产驱动也按这个判断。也就是说主线里只有同源的 **x86_64 模拟版**，**真实卡端内核从未进过主线，任何版本都没有。**

## G.3　有没有人跑过更新的卡内核

　　**没有查到先例。** 具体如下：

- Intel 自己从未换过：MPSS 3.4 到 3.8.6 全部是 2.6.38.x 这条线，MPSS 4.x 只支持 Knights Landing（KNL 是正常 x86_64，所以这条线自然终止）。
- 唯一一次公开尝试（2015 年 Stack Overflow 的「Booting custom kernel on xeon-phi」）死在引导器上：报错原文是 `mykernel.img is not k1om Linux bzImage`，因为他的产物是 `elf32-i386` 而不是 `elf64-k1om`。回答者也说清了根因：MPSS 对内核做了修改，其中之一是**为保存上下文必须支持卡上更大的寄存器组**。
- 社区那些 MPSS fork（jjkeijser、quantum-ml-geek 等）**全部只动宿主侧**：它们把 `mpss-modules` 也就是宿主 `mic.ko` 往新内核上拖。这里有个常见误解要澄清 —— `make MIC_CARD_ARCH=k1om` 只是**在宿主模块里选择卡端代码路径**，它不产出卡内核。这与本报告第三、六章的发现一致：那棵树是一树两端。
- `lore.kernel.org` 上搜 k1om 只有工具链噪音，**从来没有过 `arch/x86` 的 k1om 移植提交**。

## G.4　决定性的硬件事实：没有 SSE2

　　这一条是纯软件绕不过去的：k1om 的 CPUID 里 **MMX、SSE、SSE2 全部为 0**，也没有任何 XMM 寄存器，取而代之的是 32 个 512 位向量寄存器与 8 个 16 位掩码寄存器，以及一套私有的 4 字节前缀。

　　问题在于 **SSE2 是 x86-64 的架构基线**：SysV AMD64 调用约定用 XMM 传浮点参数，现代 x86 内核与编译器到处假设它存在。所以 k1om **不是一个合法的 x86-64 目标**，无论内核配置怎么写。Intel 自己也是这么处理的 —— 给它一个独立的 ELF 机器类型与独立工具链，而不是塞进 x86-64。

　　（顺带纠正一个流传的说法：KNC 并不是 AVX-512 实现，它的向量指令是私有编码；「AVX-512F/CD/ER/PF 子集」是后来追认的叫法，卡端 ISA 手册里连 EVEX 这个词都没有。）

## G.5　若真要做：前向移植的范围

　　把 Intel 树里与卡有关的东西分成四块，规模如下（行数与文件数取自本地那棵卡端内核树与宿主模块树）：

| 工作块 | 内容 | 规模 |
|---|---|---|
| 架构个性 | `MK1OM`／`X86_MICPCI` 相关的 `arch/x86` 改动，含 SBox 时钟源、缓存刷新、`i387`／XSAVE 路径（其中一条已知 errata 是必须强制置位 `MXCSR.DUE`）、CPU 探测、入口与 ptrace 分支、两套链接脚本布局 | 约 3 到 5 千行（本报告早先统计的 28 个文件、63 行只是「显式带 k1om 字样」的那部分，真正的实现文件另有其数） |
| 平台驱动 | `drivers/micpm/`，含 idle、cpufreq、TMU 与 MCA，另有 `michvc` 与 `ramoops` | 约 7 千行 |
| 卡端传输与服务 | `micscif`、`dma`、`pm_scif`、`vnet`、`vcons`、`mpssboot`、`ras`、`ramoops`、`virtio`、`blcr` | 24 个文件、20,232 行 |
| 引导契约 | 宿主与卡两端共享的 `bootparams` 结构，以及卡端 `mpssboot` 连着 SCIF 端口 `MIC_NOTIFY`（`include/scif.h:175` 定义为 161）向宿主报告引导完成；宿主侧在 `host/acptboot.c:152` 绑定同一端口 | 契约很小，但错一处就永远到不了 `online` |

　　好消息是**第三块与宿主端是同一批源码**：本报告移植宿主侧时打的二十多条补丁、以及那份「一树两端」的构建分流，到了卡端大体可以照搬，这一块的风险反而比架构块低。真正的难点在第一块与第四块。

## G.6　工作量与风险

　　以「能在 MPSS 下引导起来并 ping 通」为目标，一个有内核经验的开发者、卡在手边、宿主环境可用的情况下：

| 工作流 | 估计 |
|---|---|
| 在 4.18／4.19 上把 `MK1OM`＋`X86_MICPCI`＋`micpm`＋时钟源＋浮点／XSAVE 拉起来 | 6 到 10 人周 |
| 卡端驱动移植（SCIF、DMA、vnet、vcons、ras、virtio、blcr、mpssboot） | 4 到 8 人周 |
| 重新打通 `mpssd`／bootparams／端口 161 握手与镜像打包，让状态走完 `ready→booting→online` | 3 到 6 人周 |
| 用户态与 initramfs 适配 | 1 到 3 人周 |
| 合计 | **约 4 到 7 人月** |

　　目标版本建议 **4.18／4.19**：社区把同一族驱动拖到的那一代就是它，缺少的接口补丁模式也最接近。5.4 再加 2 到 4 人月，5.10 以上要翻倍 —— 因为还得把主线当年删掉的代码加回来，再在它之上做移植。

　　风险按大小排：

1. **引导契约是黑盒。** 卡上的引导 ROM 与 MPSS 加载器会校验镜像，改动编译期布局（链接脚本、`MIC_KERNEL_VERSION_20626` 这类符号）可能让一个本来正确的内核只换来一句 `not k1om Linux bzImage` 或干脆静默。唯一那次公开尝试就死在这里。
2. **SSE2 缺失。** 现代 x86 代码与其工具链不断加入新的基线假设，这是一场持续对抗。
3. **无文档的芯片 errata。** 已知的只有强制 `MXCSR.DUE` 那一处注释，其余散落在 MCE、MTRR、TSC、APIC、ptrace、进程切换的 `#ifdef` 里，等于逆向 Intel 的内部知识。
4. **没有上游、没有评审、没有未来。** 主线已按「设备停产」删除该家族，binutils 也删了 k1om，任何移植都是永久私有分支。
5. **硬件脆弱。** GDDR5 的 ECC、温度与 PCIe 链路由固件管理，新内核的电源与 idle 管理一旦与固件打架，可能把卡的引导状态弄坏。

## G.7　建议

　　分两种情况：

- **目标是「能用」**：不要动卡内核。走两条轻量路线之一 —— 一是把上游后来修掉的几个 `micscif`／SCIF／VOP 缺陷回补进 2.6.38.8 再重编；二是**给卡换一套新用户态**（用 k1om 工具链编新的 BusyBox 与 OpenSSH，重做 MicDir 再让 `mpssd` 打包成 initramfs），这样能在不碰内核的前提下消掉 2019 年那套软件的安全债。第二条与附录 F 共用同一套工具链前置。
- **目标是「研究」**：先做一个**两到三周的时间盒实验**，只验证一件事 ——「用自己编的工具链重建一棵 `ARCH=k1om` 的 2.6.38.8 内核，能否在 MPSS 3.8.6 下正常引导」。这一步能把最大的未知（引导契约）证实或证伪，再决定是否投入 4.18 的移植。**不要跳过这一步直接开始 4.18。**

## G.8　与本报告其余部分的关系

　　这一节与正文并不矛盾，反而互相印证：正文证明宿主侧的移植不需要动卡（卡自己跑自己的 Linux，宿主只灌镜像、敲门铃），而本节说明**卡的这一侧一旦要动，代价远高于宿主侧** —— 因为宿主侧面对的是接口漂移（可枚举、可清零的苦工），卡侧面对的是架构不兼容（`EM_K1OM` 与缺失的 SSE2）与一个黑盒引导契约。

　　也就是说：本项目的移植成果**不因卡内核老旧而贬值**，恰恰相反，宿主侧打通之后，卡可以继续作为一个稳定的计算设备使用很多年；真正需要更新的那部分（用户态软件栈）与内核无关。
