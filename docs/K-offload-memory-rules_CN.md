# 附录 K　Offload 内存搬运的用户侧约束（实测版）

　　本附录只讲一件事：**在 KNC 上做 offload 时，缓冲区该怎么切、窗口该怎么开**。每一条都有真机实测依据，不是推测；依据的出处写在每条后面。

## K.1　先记住一条不变量：窗口的「段数」≤ 512

　　SCIF 注册窗口时，驱动会把窗口切成一串「连续段」（`struct scif_pinned_pages.num_pages[]`），**每个段一段页数**；这份段表要送到对端。实测发现：**卡端送来的段表只写进了前 512 项**，其后的项保持为 0（原始值 `0x0`，不是"裸地址"），而 512 正是卡端 4 KiB 页时的 `NR_PHYS_ADDR_IN_PAGE`（一页放 8 字节地址 × 512 项）。

```text
RAW-SCAN:      type=2 nr_pages=8192 chunks=527 raw_sum=8177 raw_zeros=15
RAW-HEAD[0]:   raw=0x100003bc830000  pages=1  addr=0x3bc830000
RAW-TAIL[511]: raw=0x100003ba820000  pages=1  addr=0x3ba820000
RAW-TAIL[512]: raw=0x0               pages=0  addr=0x0        ← 从这里起全部为 0
```

　　后果：宿主眼里窗口末尾这些段"不存在"，写到那里就查不到地址。**修好之前**这会触发 `BUG_ON` 并把整个 SCIF 通路拖死（进程 `D` 状态、只能重启）；**修好之后**宿主会在 DMA 边界拒绝这次拷贝并打印 `DESC-BAD … refusing the copy`，用户态 `scif_writeto` 返回 `EINVAL`。

　　注意段数**不等于**字节数除以页大小：普通页一段一页，大页一段可到 2 MiB 边界。所以 32 MiB 的卡端窗口是 **527 段**（512 个单页段 + 15 个 2 MiB 段），而不是 8192 段。**判据是段数，不是大小**。

## K.2　四条编写约束

| # | 约束 | 为什么 | 依据 |
|---|---|---|---|
| 1 | **注册窗口宁小勿大**：单窗口建议 ≤ 1 MiB（宿主 16 KiB 页 = 64 段；卡端 4 KiB 页 = 256 段） | 段数远离 512 边界；T8 用 1 MiB 窗口跑通 64 MiB／256 MiB／4 GiB 全部 12/12 | 实测：1 MiB 窗口三档全绿；32 MiB 窗口（527 段）必失败 |
| 2 | **大数组不要"整块注册 + 整块搬运"**：按窗口切片，宿主循环 `scif_writeto`，卡端循环收 | 窗口大小与搬运总量解耦；总量可以远超窗口 | 实测：4 GiB 总量 + 1 MiB 窗口 = 12/12，两端 checksum 逐位一致 |
| 3 | **单次 `scif_writeto` 可用到 1 MiB**（与本条规则的窗口上限一致） | 2026-10-07 阶梯实测：26496 B → 64/128/256/512 KiB → 1 MiB 全部两端 checksum 一致；26496 只是历史保守值 | `tests/extra/x03_rma_ladder.sh`；`MAX_DMA_XFER_SIZE` = 512 KiB（宿主）只是描述符切分单位，不是安全边界 |
| 4 | **pin 内存受 `RLIMIT_MEMLOCK` 限制**：大缓冲要么分块注册，要么显式提高限制（`ulimit -l`） | `__scif_check_inc_pinned_vm()` 会拒绝超限的 pin | 源码 `micscif_api.c`；失败返回 `-ENOMEM`/`EPERM` |

## K.3　运行前怎么自查（三种办法，按成本递增）

1. **看 dmesg**（默认构建即可，这几个探针是常开的）：
   - `MIC scif DESC-INCONSISTENT …` → 对端描述不完整，本次传输会失败；
   - `MIC scif DESC-BAD (…) … refusing the copy` → 宿主已拒绝，用户态会收到 `EINVAL`；
   - `kernel BUG at` / 进程处于 `D` 状态 → 说明跑的是**未含这些修复的旧模块**，需要更新模块。
2. **看窗口几何**：用带诊断的构建（`make MIC_DEBUG=1`）会打印 `MIC scif WND: … nr_pages=… nr_contig_chunks=…`，直接读到段数；建议在标定新窗口大小时这样做。
3. **跑标定**：`TEST_BIG=<总量> TEST_BIG_WINDOW=<窗口> bash tests/t8_bigxfer.sh`，用两端 checksum 与 dmesg 判据确认。

## K.4　两点容易误解的地方

- **"12 位页数字段"不是这里的限制。** 每个连续段的页数确实只有 12 位（上限 4095 页），但驱动的分段规则是"普通页一段一页、大页一段到 2 MiB 边界"，单段最多 512 页（4 KiB 页时），**离 4095 还差 8 倍**，永远碰不到。本附录 K.1 说的 512 是**段表项数**的上限，与那个 12 位字段无关。（该字段仍被用作防御：`scif_register` 会在单段超过 4095 页时直接拒绝。）
- **这不是 LoongArch 才有的问题。** 卡端代码在 x86 上一模一样，阈值也一样；MPSS 自带的工具没注册过这么大的窗口，所以没暴露。宿主侧的页大小差异影响的是**另一族**问题（协议页 4 KiB 与宿主页 16 KiB 的换算，见[附录 I](I-page-size-alignment_CN.md)）。

## K.5　当前状态与后续

| 项目 | 状态 |
|---|---|
| 1 MiB 窗口（推荐用法） | ✓ 已验收：64 MiB／256 MiB／4 GiB 各 12/12，4 GiB 两端 checksum 逐位一致（`0x76ac888ab487e57b`），链路侧 ≈3.3 GB/s（Gen2 ×8），端到端 ≈119 MB/s |
| 大窗口（>512 段） | ✗ 卡端段表不完整；宿主已能干净拒绝并给出完整现场，**不再 panic/卡死** |
| 根治 | 需更新**卡端模块**（段表传输的第二页迭代），宿主侧无法补齐；卡端模块目前是未打补丁的上游版本 |
| 用户侧 | 按 K.2 四条约束编写即可，无需关心卡端实现 |
