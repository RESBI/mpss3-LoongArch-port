# 附录 J　验收测试套件：把「能跑」变成「可复核」

　　前面各章回答的是「要改哪些行」，附录 E、H、I 记的是「改完跑出了什么」。本附录补上最后一环：**这些结论怎么被别人重新验证一遍。** 随发布版交付一套脚本（发布树里的 `tests/`），它把「这次移植到底能不能用」拆成 T0–T8 八个阶段，每一条判据都对应移植过程中真实踩过的一个坑；跑一遍就知道结论是否仍然成立。

---

## J.1　它是什么，放在哪

| 项 | 内容 |
|---|---|
| 位置 | 发布树内的 `tests/`（与 `00-build-tools` … `09-boot-images` 平级） |
| 入口 | `run_all.sh`（编译 → 安装 → 测试）、`run_tests.sh`（只做功能测试，**普通用户**即可） |
| 单阶段 | `t0_build.sh` … `t7_nbody.sh`，可 `--only tN` 单独跑 |
| 日志 | 每次运行单独成目录 `tests/logs/run-<时间戳>/`，逐阶段 `T*.log` 加逐档 `T7-tier*.log` |
| 规模 | `--quick` 降一档；`TEST_N`／`TEST_N2`／`TEST_N3`／`TEST_ROUNDS` 可精细覆盖 |

　　之所以把「普通用户即可运行」当成硬要求，是因为它本身就是被测性质之一：这套移植的目标是「卡能被普通用户使用」，凡是需要 root 才能完成的步骤（编译、装模块、装 udev 规则）都被隔离在 T0／T1 两个阶段里。

## J.3　真机实测结果（2026-10-06）

　　环境：龙芯 3A6000（AOSC OS 13.3.1，内核 `7.1.13-aosc-main-16k`，16 KB 页）＋ Xeon Phi 7120P，卡 `online`，卡端 `coi_daemon` 在跑。全部功能阶段以**普通用户**执行。

| 阶段 | 通过 | 失败 | 跳过 | 要点 |
|---|---:|---:|---:|---|
| T2 | 8 | 0 | 1 | 卡端内核 `2.6.38.8+mpss3.8.6`；交叉编译 10840 字节、部署 md5 一致、卡上打印 `HELLO_FROM_CARD`。跳过 1 项为「卡端 rootfs 类型识别」（BusyBox `mount` 输出不匹配判据，纯提示性质） |
| T3 | 11 | 0 | 0 | 64 字节与 26496 字节往返均 0 不符；卡端主动消息与双向 fence 齐全 |
| T4 | 15 | 0 | 0 | 七档长度逐字节正确；26496 字节全量校验 0 不符；无非对齐访问异常 |
| T5 | 17 | 0 | 0 | 建进程 `COI_SUCCESS(0)`、240 线程、归约相对误差 **−3.35e-16**、收尾后 daemon 仍在 |
| T6 | 12 | 0 | 0 | 三轮 n＝2×10⁷／2×10⁸／1×10⁸，卡上 0.14／0.37／0.29 秒，误差 −1.40e-16／−2.24e-16／0；每轮后 daemon 存活、内核零异常；压完仍能正常 offload |
| T7 | 9 | 0 | 0 | 见下表 |
| T8 | 12 | 0 | 0 | 卡端 4 GiB 大块 `malloc`（逐页 touch）＋ 1 MiB 窗口注册；4 GiB 全量传输、两端 checksum **逐位一致**；静默构建下端到端 119.3 MB/s、`scif_writeto` 内 3478 MB/s；无内核异常 |

　　N 体引力 $O(N^2)$ 三档（卡端自行生成初始条件，结果经返回区回传）：

| 档 | N | 步数 | 线程 | 校验和与宿主参考 | 能量相对误差 | 卡上耗时 | 算力 |
|---|---:|---:|---:|---|---:|---:|---:|
| 1 | 1024 | 20 | 240 | **差 0.000e+00（逐位一致）** | 1.96e-04 | 0.40 s | 0.62 GFLOPS |
| 2 | 8192 | 10 | 240 | —（规模大，只查能量守恒） | 8.47e-05 | 3.1 s | 2.10 GFLOPS |
| 3 | 16384 | 5 | 240 | — | 4.02e-05 | 5.1 s | 2.68 GFLOPS |
| 4 | **窗口复用时的暂存区不能与窗口 0 的目的地重合** | 窗口注册在大缓冲开头时，后续每个窗口的入站数据都会覆盖窗口 0 刚放好的数据 —— 表现为「后面都对、头 1 MiB 错」 | T8 卡端单独开一块暂存区注册窗口，每窗口都从暂存区拷入大缓冲；并对每个窗口各算一次 checksum 比对，差错直接定位到窗口号 |
| 5 | **大窗口的页数与段跨度必须按「哪一侧的页」解释**（详见[附录 I](I-page-size-alignment_CN.md) I.12） | 宿主自身窗口页数被 ×4、对端窗口页数被 ÷4，导致解映射多 4 倍（`mic_smpt.ref_count < 0`）与查找失败（`micscif_get_dma_addr` BUG） | T4 之后**再等 30 秒**查 dmesg（事故在 workqueue 里晚几秒才炸，T4 自己的检查看不到）；T8 走 1 MiB 多页段窗口，专门覆盖「页数 ≠ 段数」那条分支 |

　　T8 大数据量传输三档（宿主 → 卡，卡端逐窗口校验并整缓冲校验）：

| 档 | 数据量 | `scif_writeto` 内耗时带宽 | 端到端带宽 | 卡端整缓冲校验 | 两端 checksum |
|---|---:|---:|---:|---:|---|
| 1 | 64 MiB | 2978.8 MB/s | 118.3 MB/s | 0.28 s | 一致 ✓ |
| 2 | 256 MiB | 3835.3 MB/s | 123.7 MB/s | 1.14 s | 一致 ✓ |
| 3 | 4096 MiB | **3478.1 MB/s** | **119.3 MB/s** | 18.34 s | **逐位一致 ✓**（`0x76ac888ab487e57b`） |

　　两个数字的含义不同，都要看：**`scif_writeto` 内耗时**只统计该调用自身，反映 PCIe＋DMA 侧的搬运能力；**端到端**还要等卡端对每个 1 MiB 窗口做校验与搬运，所以低一个数量级。链路实际是 **PCIe Gen2 ×8**（`lspci`：`LnkCap x16`、`LnkSta Width x8 (downgraded)`，5 GT/s ×8 ≈ 4 GB/s 理论），3478 MB/s 正落在它的实际能力区间。

　　⚠️ **口径更正**：早先报告过"链路侧 325.9 MB/s"，那是**测量假象**——当时的诊断打印（`pr_info`）就在 RMA 拷贝路径里，每个 26496 字节的片段要打几十行日志，耗时被打印本身主导（见同日"诊断打印改为构建选项"一节）。关掉打印后同一指标变成 3478 MB/s。凡与打印相关的耗时数字，都要在静默构建下重测。数据完整性由两端 checksum 保证：宿主算源缓冲、卡端算收到的整缓冲，并**逐窗口**各算一次以便把差错定位到具体窗口。

　　合计功能阶段 **84 项通过、0 项失败、1 项跳过**。T0／T1 需要 root 且会改动系统（写 `/usr`、装模块），本轮没有重跑；它们在 2026-10-05 的发布验收里已按同一脚本走过一遍。

## J.4　测试里固化的五条实测坑

　　这五条都是移植过程中先踩后修的，现在写进脚本，**改动一旦把它们碰坏，测试会直接红**：

| # | 约束 | 不满足时的现象 | 脚本里的判据 |
|---|---|---|---|
| 1 | 卡端 sink 必须 **`-rdynamic`** | 导出符号不在 `.dynsym`，卡端 `dlsym` 失败，宿主收到 `COI_DOES_NOT_EXIST(5)` | T5／T7 编译后 `readelf --dyn-syms` 必须看到 `CardReduce`／`NBodyRun` |
| 2 | 卡端 sink 的**优化档必须逐源码实测** | `-O1`／`-O2` 编出的 N 体 sink 在卡上立刻崩（卡端日志 `segfault at 0`，崩溃 ip 落在一条 `vpackstorelpd` 上）；而归约 sink 用 `-O2` 却完全正常 | T7 固定 `-O0` 且三档必须全部跑通；T5／T6 沿用 `-O2`（实测 17／17 通过）。**换优化档前先跑一遍** |
| 3 | **`COIBufferCreate` 不可用**（`COI_OUT_OF_MEMORY(13)`） | 大数据无法一次性送入 | T5／T7 改用「宿主只传几十字节参数 ＋ 卡端按确定性公式生成」，结果走返回区（≤64 KiB 入、64 字节出） |

| 6 | **单个连续段的页数不能超过 4095**（线上窗口描述只有 12 位，见[附录 I](I-page-size-alignment_CN.md) I.12.6） | 超限的段被 `RMA_SET_NR_PAGES` 静默截断成 0 → 段跨度算成 0 → `micscif_get_dma_addr` 扫完所有段仍找不到地址而 `BUG_ON(1)` → 注销无限重试 → 进程 `D` 状态 | `scif_register` 在 pin 之后、接触对端之前直接拒绝并打印是哪一段超标（`-EINVAL`）——把"必然卡死"变成"一次干净的注册失败"；T8 的窗口保持 1 MiB |

　　第 2 条还带一次自我更正：早先给出的自查法是「反汇编里 `vpackstore` 必须为 0 条」，2026-10-06 用正确的 k1om objdump 复核后否证 —— 跑得通的 `-O0` 产物里同样有 12 条，崩掉的 `-O1`／`-O2` 反而各只有 11 条。**条数不是判据，能不能在卡上跑通才是**，所以 T7 里那一项已从「断言」降为「参考信息」。完整证据见[附录 H](H-offload-field-notes_CN.md) H.14。

## J.5　两条判据设计上的经验

1. **用「校验和逐位一致」代替「有没有结果」。** 卡端算一个确定性校验和放进返回区，宿主用自己的参考实现算同一个数比对。这一条同时抓住「算错」与「传错」两类故障；N 体示例正是靠它才发现前端「交错数组别名」写法的错误（卡端与宿主对不上 6.1e-04，改成分离数组后逐位一致）。
2. **校验要能定位，不能只给「不一致」。** T8 的第一版只在最后比一个整缓冲校验和，结果只能得到「两端不一致」；改成**每个 1 MiB 窗口各算一次**之后，差错直接落到窗口号与偏移上，一眼看出是「头 1 MiB 错、其余正确」——那是暂存区被覆盖的特征，而不是传输错误。判据的粒度决定了排查的速度。
3. **自查规则要有对照样本。** 判断「某条指令是否存在」时，必须同时量一个已知可用的样本（这里就是 T5 的 sink）；否则一条失败的测量命令会被当成「0 条命中」的通过信号 —— J.4 第 2 条的错误规则就是这么活下来的。

## J.6　复现命令

```bash
# 全流程（编译 → 安装 → 功能测试）；T0/T1 需要 root
sudo bash tests/run_all.sh

# 只做功能测试（普通用户即可；前提：已安装、mic 已加载、卡已 online）
bash tests/run_tests.sh

# 单个阶段 / 快速规模
bash tests/run_tests.sh --only t7
bash tests/run_tests.sh --quick

# 编译不过时先跑它：只编译、不接触卡
bash tests/precheck.sh

# 单独验证「非 root 使用」这一场景（需要 root 改设备权限）
sudo bash tests/perm_probe.sh
```

　　offload 相关阶段（T5／T6／T7）还需要移植者手上的三样东西：k1om 交叉编译器、k1om sysroot、卡端依赖库目录（含自建的 k1om `libgomp.so.1`）。它们的位置由 `tests/lib/common.sh` 里的 `K1OM_SDK`／`K1OM_CXX`／`COSLIB` 给出，可用环境变量覆盖；卡地址默认 `<card-ip>`（`CARD_HOST` 可覆盖）。
