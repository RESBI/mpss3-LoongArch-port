# 附录 N12 — T7 N 体：剩下那 90% 在哪里

T7 在 N ≥ 65536 时中位吞吐约 105 GFLOPS——是同一份输入上标量 `-O0` 实现的约 35 倍，
占该卡约 1208 GFLOPS FP64 峰值的 **8.7%**。本篇回答「还有没有余量」，
而且是照着实测写的：四次想跑得更快的尝试都没成功，另有一处应该有效的结构性改动
尚未动手。

## 1. 周期账，这次算对了

本篇早先的草稿在这里错了整整一倍——它用错了迭代次数去摊周期预算，于是得出
「内核只跑到发射上界的 34%」。修正后的账，用的是从构建产物里抠出来的内层 `j` 循环：

| | 每轮迭代（16 对） |
|---|---|
| 循环内指令总数 | **119** |
| 其中 FP 流水线类（FMA / 乘 / 减 / 加 / 比较 / getexp / getmant） | **78** |
| `vbroadcastsd` 加载 | 4 |
| `vprefetch0` | 4 |
| `vmovapd` 寄存器搬移 | 7 |
| 循环开销 | 8 |

在两个大档上反推周期：

| | 档位 5 (N=65536) | 档位 6 (N=131072) |
|---|---|---|
| 每核向量迭代次数 | 1.76 × 10⁷ | 7.05 × 10⁷ |
| 每核周期数 | 2.03 × 10⁹ | 7.95 × 10⁹ |
| **每轮迭代周期数** | **115** | **113** |
| **每周期指令数（IPC）** | **1.04** | **1.05** |

也就是说内核每周期发射约 1.05 条指令，而 FP 流水线——这个核上每周期一条 512-bit
FP64 操作——在其中 78 个周期是满的。**它跑到了自己 FP 发射上界的 69%**；
对一个没有乱序窗口的顺序核、对这个指令组合来说，这已经接近实际天花板。

这个模型给出一个可否证的预测，而它成立：把倒数平方根整个删掉会去掉 78 条 FP 中的
56 条（2 块 × 28），只剩 22 条，因此理论上值约 3.5×。档位 6 实测：
**289.8 GFLOPS 对 109.7——2.6×。** 与 3.5× 的差距就是那些非 FP 指令，它们不会消失。

## 2. 四件没起作用的事

每一件当初都是合理的想法。全部实测过，没有一个把数字推出噪声范围。

| 尝试 | 档位 5/6 结果 | 结论 |
|---|---|---|
| 对四条加载流加 `vprefetch0`，距离 0/4/8/16/32/64 | 距离 16 时 +2.3%，其余无 | 小幅，保留 |
| 用对齐的 8 车道 `_mm512_load_pd` 替代四次广播 | 92.7 对 98.4 | **更慢** |
| 以指数为变量的 9 次多项式，无比较、无掩码 | 99.84 对 98.81 | 打平 |
| **手工 lockstep 交错两条 `rsqrt` 链** | 106.8 / 110.0 对 95.4–109.3 | **打平** |

lockstep 那件值得解释，因为它背后的推理是对的，而且反汇编也证实了前提。
GCC 把两次 `rsqrt_pd` 内联成的序列**没有交错**：内层循环里块 0 的 `vgetexppd`
比块 1 的早约 30 条指令，中间隔着块 0 整条依赖链。在顺序核上，这意味着第二个块
必须等第一个块停顿完才能发射——这正好解释了为什么两块展开只买到 +4%。

于是手工写了 `rsqrt_pd_2`，逐条交替两条链。**没用。前提是真的，但无关紧要**：
§1 表明内核是均匀地受 FP 发射限制（约 1.05 IPC），而不是受依赖链延迟限制，
所以那份额外的独立性没有停顿可填。GCC 另外还把一部分配对重新分开了，
这也提醒：调度器没有义务尊重源码里独立操作的顺序。

## 2b. 架构级旋钮：一个实测持平，一个实测做错了

### 线程数那次扫描是无效的，而更正很重要

本节最早的版本报告说「每核线程数与线程亲和性都持平」。**那些测量毫无意义。**
宿主是用 `COIProcessCreateFromFile` 把卡端进程拉起来的，而**宿主的环境变量
跨不过这条边界**——所以 `OMP_NUM_THREADS=61`、`=122`、`=183`、`=244`
跑的都是同一套 240 线程配置。只要核对一下内核自报的线程数，问题立刻现形：

| 想设成 | 内核自报 |
|---|---|
| `OMP_NUM_THREADS=61` | **240** |
| `OMP_NUM_THREADS=122` | **240** |
| `OMP_NUM_THREADS=183` | **240** |
| `OMP_NUM_THREADS=244` | **240** |

修法是把线程数做成**参数**传进去，在卡端调 `omp_set_num_threads()`。
`Params` 增加了 `nthreads` 字段，宿主侧由 `T7_THREADS` 填。已验证：
`T7_THREADS=61 → 61`、`=183 → 183`、`=244 → 244`。

> **规则。** 在卸载目标上，宿主设的环境变量不是参数。
> 如果测量没有确认设置真的生效，那它就没有生效。

### 真正的扫描

MPairs/s，best-of-7，逐档：

| `T7_THREADS` | 线程/核 | tier 3 | tier 5 | tier 6 |
|---|---|---|---|---|
| 61 | 1.0 | 2257.81 | 2403.27 | 2490.88 |
| 122 | 2.0 | 2974.41 | 3686.00 | 4005.63 |
| 183 | 3.0 | 3559.64 | 4399.92 | 4721.80 |
| 220 | 3.6 | **3983.79** | 5020.38 | 5172.21 |
| **240** | 3.9 | 3502.82 | **5354.48** | **5580.94** |
| 244 | 4.0 | 2895.88 | 4479.18 | 5001.22 |

三个结论，前两个与本节此前的说法相反。

1. **线程数影响很大。** 从每核 1 线程到 4 线程，吞吐翻倍还多
   （tier 6 上 2491 → 5581 MPairs/s）。SMT 在这里值约 2.2×，
   所以此前「单线程已经吃满核」的说法是那次坏扫描的产物。
2. **超订比留一个核空闲更糟。** 244 线程——卡上每一个硬件线程——在 tier 6 上比
   240 线程**慢 10%**，而 240 是 61 个核里用 60 个、每核 4 线程。
   有别的东西需要跑：COI 守护进程和内核自身的工作。运行库默认就选 240，
   所以出厂配置本身就是好的那个。
3. **小档偏好更少线程。** tier 3 在 220 上最好（比 240 高 14%），
   因为它 2048 个向量块在没有最后一个核的线程时分配得更均匀。
   那一档本来就由固定开销主导，所以不改变任何结论，
   但它解释了为什么存在逐档最优。

`T7_THREADS` 现在是受支持的旋钮（`T7_THREADS=220 bash t7_nbody.sh`）。

### 线程亲和性：仍未测量

`GOMP_CPU_AFFINITY` 与 `OMP_PROC_BIND` 同样是宿主环境变量，**同样没有到达卡端**，
所以此前关于亲和性「持平」的读数不构成任何证据。要在卡上绑核，
需要在 sink 里调 `sched_setaffinity`。这还没试过；而考虑到 240 线程——
一个朴素的 `schedule(static)` 分块——已经落在已找到最好数字的 10% 以内，
为它做这套管线并不显然划算。

### 确实持平的部分

编译期旋钮是真实测量，因为它们改变的是发出的代码而不是运行环境：

| 手段 | 扫描范围 | 结果 |
|---|---|---|
| 代码对齐（配对指令解码窗口） | `-falign-loops` 16/32/64/128，`-falign-functions=64` | 111.2–112.0 GFLOPS —— 持平 |
| 预取提示 | `vprefetch0` / `1` / `2` / `NTA`，距离 16 | 111.0–111.9 —— 持平 |
| 预取距离 | 0 / 4 / 8 / 16 / 32 / 64 | 距离 16 时 +2.3%，其余无 |

### 唯一有用的那个架构特性，被工具链堵死了

KNC 的 MVEX 编码支持**嵌入广播**：算术指令的内存操作数可以是**单个元素复制到整个向量**，
float64 写作 `{1to8}`。ISA 手册有记载（`VMULPD` 的操作数是 `Sf64(zmm3/mt)`；
MVEX 表：`001 [rax] {1to8} 8`），它能把内层循环里四条 `vbroadcastsd`
全部折进消费它们的算术指令里。

但这套工具链够不着：

| | 结果 |
|---|---|
| GCC 生成它 | 从不——`_mm512_fmadd_pd(_mm512_set1_pd(p[3]), a, a)` 产出的是 `vbroadcastsd` + `vfmadd132pd` |
| GNU as 接受它 | `vfmadd213pd (%rax){1to8}, %zmm1, %zmm0` → ``Error: junk `1to8' after expression`` |
| `vmulpd`、`vsubpd` 同理 | 同样被拒 |

手册还敲定了一件事，而 [N11](N11-t7-two-units-and-three-traps_CN.md) §4
此前只是从行为反推出来的：

> 向量指令的 8 位位移**总是乘以该指令访存的总字节数**，可能是 64、32、16、8、4、2 或 1，
> 取决于生效的广播和/或数据转换。……**disp8*N 的用法……把配对指令解码窗口所需的尺寸
> 缩小了 3 个字节。**

这就是 `vpackstorelpd` 的机理，由厂商亲口说明：位移按**元素**大小缩放，
所以同样的字节在不同操作数形式下解码出不同地址——正是这一点让 `%rbp` 相对编码能跑、
而 `0x10(%r12)` 那条崩掉。

## 2c. 嵌入广播可达——而且更慢

KNC 的 MVEX 编码允许算术指令的内存操作数成为**单个元素复制到整个向量**，
float64 写作 `{1to8}`（见 §2b）。那里把它记为「被工具链堵死」。**那是错的**，
而这个错误本身有教育意义：

| 尝试 | 结果 |
|---|---|
| 独立 `.s` 文件 | **接受** —— `vmulpd (%rax){1to8}, %zmm2, %zmm1` 编出的 MVEX 前缀字节是 `0x18`，普通形式是 `0x08` |
| 内联汇编写成 `(%2){1to8}` | 被拒：``junk `1to8' after expression`` |
| **看 GCC 生成的 `.s` 才明白** | GCC 的 asm 模板**把花括号吃掉了**：它发出的是 `vmulpd (%rdi)1to8, %zmm0, %zmm0` |
| 内联汇编写成 `(%2)%{1to8%}` | **接受** —— 生成 `vmulpd (%rdi){1to8}, %zmm0, %zmm0` |

`%{` 与 `%}` 是 GCC 的 *dialect alternative* 定界符，裸花括号因此消失。
加上转义后，编译出的核心里出现八条 `{1to8}` 指令，两路循环里的四条
`vbroadcastsd` 全部消失。

有一条约束决定了它怎么用：MVEX 的内存操作数只能落在 Intel 记法的最后一个源位置，
所以 `VSUBPD` 能算 `a − broadcast(*p)`，不能算 `broadcast(*p) − a`。
内核需要 `dx = x[j] − x[i]`，广播形式给的是 `x[i] − x[j]`，符号靠把累加从
`vfmadd` 换成 `vfnmadd` 补回。**IEEE 下符号翻转是精确的，而 `fnmadd(a,b,c)`
是 `−(a·b)+c` 的单次舍入，所以结果逐位不变**——受力核自检（6.340e-16）
与端到端校验和都未变，证实了这一点。

而它更慢：

| `NB_BCAST_FOLD` | 档位 6，best-of-3 | 受力核自检 | 校验和 |
|---|---|---|---|
| 0 —— 独立的 `vbroadcastsd` | **5567.46 MPairs/s** | 6.340e-16 通过 | 一致 |
| 1 —— 嵌入 `{1to8}` | 5204.68 MPairs/s | 6.340e-16 通过 | 一致 |

**−6.5%，而且是对的。** 可能的原因：MVEX 形式多一个前缀字节加一个位移，指令更长；
而「从内存广播」的操作数在访存端口上的行为，可能不如独立的 `vbroadcastsd`
喂给寄存器操作数。这个特性是真的，现在已经可达，但在这个内核上不划算。
开关保留在源码里（`NB_BCAST_FOLD`），默认 0。

## 3. 为什么 FP 指令数已在接近地板

每个 `i` 块的 FP 指令：

| | 条数 |
|---|---|
| `r² = dx²+dy²+dz²+soft2` | 3 |
| `1/sqrt` —— 取指数/尾数、4 步掩码缩放、5 次多项式、2 次牛顿迭代 | **28** |
| `y³ · m` | 3 |
| 三个轴的累加 | 3 |
| **合计** | **37** |

倒数平方根占其中 76%，而且压不动：

- **两次牛顿迭代是必需的。** 5 次尾数多项式的误差是 1.17e-5，一次迭代到 2.1e-10，
  过不了受力核自检 1e-14 的门槛。想靠一次迭代到 1e-14 需要 10 次多项式，
  代价比省下的那次迭代还大。
- **四步缩放是必需的。** 指数范围 `e ∈ [-12, 4]` 需要四位；三步只能覆盖
  `e ∈ [-8, 0]`，装不下实际范围。
- **无掩码写法并不更便宜。** 9 次多项式 `P(e) ≈ 2^(-e/2)` 把 4 条比较 +
  4 条掩码乘 + 4 条掩码减（12 条）换成 9 条 FMA——少三条，实测完全一样。

KNC 没有 FP64 倒数平方根可以退回去用
（[N10](N10-t7-gemm-fp64-no-transcendentals_CN.md)），所以 1 ulp 精度就是 28 条
指令的代价。

## 4. 对称性：算术上该成立、而指令集不允许的那个杠杆

最明显的结构性改动是牛顿第三定律：每对的力只算一次，`+f` 给一个天体、`−f` 给另一个。
算术上它确实诱人——按**物理**配对数来数倒数平方根的求值次数（这个区分，
本篇早先的草稿弄错了），现状是每 4 对一次，对称版是每 8 对一次。
也就是每物理对 10 → 5.5 条 FP 指令，约 1.8×。

**但这套硬件表达不出来。** 原因是结构性的，不是编程技巧问题。

现状内核按 `i` 向量化、广播 `j`，所以累加器天然落在向量车道上。
对称要求反过来：对一个块对 `(I,J)`，作用在 `J` 上的力必须累加到**被广播的那个下标**上，
而作用在 `I` 上的力累加到被向量化的那个上。于是两个累加中必有一个需要
**跨车道归约**——对每个 `i` 或每个 `j` 做一次 8 车道求和。

KNC 没有任何指令能做这件事：

| intrinsic | 汇编器判定 |
|---|---|
| `_mm512_permute_pd`、`_mm512_mask_permute_pd` | ``vpermilpd' is not supported on `k1om'`` |
| `_mm512_shuffle_pd` | ``vshufpd' is not supported on `k1om'`` |
| `_mm512_shuffle_f64x2` | `no such instruction: vshuff64x2` |
| `_mm512_permutex_epi64`、`_mm512_permutexvar_epi64` | ``vpermq' is not supported on `k1om'`` |
| `_mm512_alignr_epi64`、`_mm512_shuffle_i64x2` | `no such instruction` |
| `_mm512_swizzle_pd`（KNC 的 MVEX swizzle） | 未声明——工具链头文件里没有任何 `_MM_SWIZ_*` 常量 |

**在 FP64 向量的 512 位车道之间搬运数据，没有任何办法**——浮点 shuffle 不行、
整数置换不行、MVEX swizzle 也不行。KNC 上唯一的跨车道机制是**编码在访存操作数
内部**的 swizzle/广播（而它只能到 `{1to8}`，不是任意置换），以及内存往返。

剩下的就是内存往返，而它的代价大于收益。把一个 8 车道向量归约成标量需要：
一次 64 字节存储、一条别名屏障、然后八次广播加载加八次加法——
**每个分量约 18 条向量指令，三个轴约 54 条**，每处理一个 `i` 的一个 `j` 块就要付一次。
把它加进每对的代价里：

| j 方向块宽 | 每物理对的指令数 | 对比现状（10） |
|---|---|---|
| 1 块（8 个 j） | 13.1 | **0.76× —— 更慢** |
| 2 块 | 9.6 | 1.04× |
| 4 块 | 7.8 | 1.28× |
| 8 块 | 6.9 | 1.45× |

更宽的块需要更多驻留寄存器的状态（j 块数 × 4 个数组，再加伙伴累加器），
超过两块内核就开始溢出。**现实落点大约在 0.8–1.0×，也就是没有收益。**

> **规则。** N-body 的对称性本质上是一次 scatter，而 scatter 需要转置。
> 在一个没有车道置换的 SIMD 指令集上，先把转置的价算清楚，再数省下来的开方。
> 这里它每 64 对要花约 54 条指令，而省下的是每 64 对 28 条。

这也正是早先草稿里「约 1.5–1.8×」错在哪：它数了省下的 rsqrt，
却从没问过伙伴的力要怎么回到正确的车道上。

## 5. 不值得做的事

- **再加编译标志。** `-O2`、`-O3`、`-O3 -funroll-loops` 持平——
  档位 3 上是 52.02 / 51.34 / 48.63。
- **继续按 `i` 展开。** 两块展开只给 +4%，而三次想让第二个块有用的尝试全部落空；
  四块展开会因为同样的原因把寄存器压力翻倍。
- **去追那些非 FP 指令。** 119 条里有 41 条非 FP，最多值约 31% 的周期，
  而三次针对性尝试一无所获。
- **厂商库。** k1om 上没有。
- **继续动超越函数。** §3 就是「28 条指令是 1 ulp 精度地板」的证据。

## 6. 结论

| 问题 | 回答 |
|---|---|
| 内核相对它的指令组合算优化好了吗？ | **是** —— 1.05 IPC，FP 发射上界的 69% |
| FP 指令数还能减吗？ | **不能** —— rsqrt 已到 1 ulp 的算术地板 |
| 非 FP 开销能去掉吗？ | **三次尝试说不能** |
| 架构级调优有用吗？ | **基本没有** —— 对齐与预取提示持平；**线程数不是**（240 比 244 快 10%，§2b），亲和性仍未测量 |
| 还有大杠杆吗？ | **没有** —— 唯一候选「对称性」需要 ISA 做不到的跨车道归约（§4） |
