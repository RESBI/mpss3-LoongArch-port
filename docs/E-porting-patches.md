## E.4 — Scope and Boundaries

Three things need to be stated clearly.

First, what is changed here is what is **necessary to build and run**; nothing was refactored in the name of being "more modern". Anything that a build switch could solve (E.3) was left untouched in the source.

Second, the essence of problems like `.symver` is a **stricter toolchain**, not an architecture change: the new binutils refuses to declare a default version for a symbol that is undefined in the current object file. It passed on the 2016 k1om toolchain and fails on today's LoongArch toolchain — and it would fail just the same on today's x86-64 toolchain. This belongs to the "interface drift" category of Chapter 6, except that it happens in user space.

Third, the card-side copy of `mpssd` (`mpss-micdaemon`, 1,777 lines) is **out of scope for the port**: it runs on the card, uses the k1om binary shipped with the card image, and has nothing to do with the host architecture. What gets ported on the host side is its peer.

## E.6 — Runtime Verification: Not Just "It Builds"

Building it is not enough. This section is the result of actually calling the public APIs on real hardware; the programs and logs are kept on the server.

### Library level: the 14 libmicmgmt calls

A small program (`verify_miclib.c`) was written to call 14 public APIs, checking each one against the raw sysfs values at the same moment.

| Result | Items |
|---|---|
| **7 passed** | device enumeration (1 device), device number, `mic_open_device` returning `mic0`, `SKU` = `C0PRQ-7120 P/A/X/D`, `POST code` = `FF`, `Family` = `0x0b`, `Model` = `0x01` |
| **7 failed** | `mic_get_serial_number`, `mic_get_uuid`, `mic_get_memory_info`, `mic_get_cores_info`, `mic_get_version_info`, `mic_get_thermal_info`, `mic_is_ras_avail` |

The cause of the failures was tracked down, and it is **not a porting gap**: all seven go through `scif_request()` (34 such calls in `knc_device.cpp`), meaning they must talk to the card's `mpssd` over SCIF; and `/dev/mic/scif` has permissions `crw------- root root`, so an ordinary user cannot open it. The confirming evidence is that every sysfs-backed call (`sku`/`post_code`/`family`/`model`/device enumeration) **passes**, and those attributes really are present in sysfs (`sku`, `postcode`, `family`, `model`, `stepping`, `memsize`, `flashversion`, `serialnumber` and so on, permissions `r--r--r--`).

This boundary is worth recording: **on this machine, the "read sysfs" part of the MPSS tools needs no privilege, while the "go over SCIF" part does.** MPSS's own answer is to install `micctrl` setuid root (`INSTALL_s = $(INSTALL) -m 4755` in `micctrl/Makefile:37`), precisely for this reason.

### Library level: MYO's two key calls

When MYO was ported, the x86 `rdtsc` was replaced with `CLOCK_MONOTONIC` nanoseconds (patch 20), and that has to be measured to count:

| Call | Measured |
|---|---|
| `myoMyId()` / `myoNumNodes()` | `0` / `1` (single node) |
| Difference of `myoTicks()` across a 250 ms sleep | **250,101,315** — monotonically increasing, and exactly on the nanosecond scale |
| Difference of `myoWallTime()` over the same interval | 250,100 microseconds |

That difference is the direct evidence that the "rdtsc to monotonic clock" port works: the unit is right, the monotonicity is right, and it matches the real duration.

### Library level: COI's error path

With the card-side `coi_daemon` not running, `COIEngineGetCount()` and `COIEngineGetHandle()` return 1 and 5 respectively, with a null handle — **returning an error code gracefully instead of crashing**. What this verifies is the error path: the failed SCIF connection in `libcoi_host.so` is correctly translated into a COI error code.

### Boundaries

The common boundary of these verifications is that **functionality depending on card-side services (the SCIF management channel, the COI daemon, the MYO service) was not verified in a state where it was not installed to the system paths and not running as root**. Those must wait for the system installation step (`g9_00_install_root.sh`) to complete, where the same probe set is rerun as root and these cells are filled in.

### E.7.2 — Two Behavioral Constraints (Not in the Documentation; Only Measured)

**The first: SCIF and sysfs have different privilege boundaries.** Among the `verify_miclib` items, the dividing line between the 7 that failed and the 7 that passed is exactly "read sysfs" versus "go over SCIF": device enumeration, SKU, POST code, Family and Model read `/sys/class/mic/mic0/*` (permissions `r--r--r--`) and are available to an ordinary user; serial number, UUID, memory information, core information, version information, temperature and RAS go through `scif_request()` (34 places in `knc_device.cpp`) and must first open `/dev/mic/scif`, which is a `crw------- root root` device. This also explains why MPSS installs `micctrl` setuid root (`INSTALL_s = $(INSTALL) -m 4755` in `micctrl/Makefile:37`).

**The second: the card-side mpssd's MONITOR_START handshake has a timing constraint.** The card-side `mpssd` starts up in this order —

```text
1. bind port 163 (MPSSD_MONSEND) and listen
2. scif_connect({node 0, port 160 = MPSSD_MONRECV}) to the host mpssd, send MONITOR_START
3. scif_accept, waiting for the host to connect back to 163
4. only after the handshake succeeds, pthread_create(micctrl_mon) -- port 164 (MPSSD_MICCTRL) is bound only at this point
```

In other words: **the host mpssd must already be listening on port 160 at the moment the card-side mpssd starts**, otherwise nobody answers that MONITOR_START in step 2, port 164 never appears, and every subsequent operation that goes through `MPSSD_MICCTRL` (for example `micctrl --useradd`) connects to a listener that does not exist. Our first round hit exactly this trap: we had bootstrapped the card by hand through sysfs with the host mpssd not running. Restarting the card-side mpssd while the host mpssd was running completed the handshake immediately (the last two rows of E.7.1 are the evidence).

### E.7.3 — One Original Code Defect: a Failed Connection Retries Forever in the Kernel

The wait loop starting at `micscif/micscif_api.c:728` deserves a note of its own:

```c
while ((err = wait_event_interruptible_timeout(ep->conwq,
        (ep->state != SCIFEP_CONNECTING), NODE_ALIVE_TIMEOUT)) <= 0) {
    ...
retry:
    err = wait_event_timeout(ep->diswq, (ep->state != SCIFEP_CONNECTING), NODE_ALIVE_TIMEOUT);
    if (!err && scifdev_alive(ep))
        goto retry;          /* peer not answering and the device is still alive: retry forever */
    ...
}
```

When the connection target does not exist: wait for the timeout → send a termination message → wait again → still no answer → `goto retry`. The whole thing loops in the kernel and **never returns to user space**, so neither `SIGTERM` nor `SIGKILL` can terminate it (the SIGTERM sent by `timeout 300` makes no difference either) — in our measurements that is how a `micctrl --useradd` turned into an unkillable process, and the only way out was to reset the card so that `scifdev_alive()` became false. This is the behavior of the original code (a peer that answers normally never reaches this path), not something introduced by the port, but it bites in the most common debugging scenario, "the peer is not up", so it is worth recording.

### E.7.4 — Closed Loop: micctrl Creates a User on the Card and Injects Keys

Once the timing constraint of the second point in E.7.2 was satisfied, the original question — "how does micctrl create users and inject keys on the card" — ran all the way through on LoongArch. A single `micctrl --useradd=resbi` did two things:

First, **offline**: it writes the `resbi` line into `etc/passwd` in the host-side card image directory, and collects the `*.pub` files under the host user's `~/.ssh` into `<MicDir>/home/resbi/.ssh/authorized_keys` (this is exactly the behavior of `add_ssh_info()` and `create_authfile()`, see §4.8 of Chapter 4).

Second, **online**: over SCIF it pushes the same content to the running card — `adduser_remote()` at `user.c:1500` connects to `{node 1, port 164}` and, following the opcode table starting at `libmpsscommon.h:43`, sends `MICCTRL_ADDUSER`, then `MICCTRL_AU_FILE` for each file, then `MICCTRL_AU_DONE`. The card-side `mpssd` writes it to disk and logs one line:

```text
Sun Oct  4 19:48:42 2026: [UserAdd] 'resbi' Success
```

A subsequent `ssh resbi@171.31.1.2` logs in directly (`uid=1000(resbi) gid=1001`) — this user and its keys were both created by micctrl and sent up over SCIF, with no hand-editing of the card-side image.

One harmless warning, worth noting in passing: `[Warning] mic0: Create home directory /var/mpss/mic0/home/resbi failed: File exists` — `--initdefaults` had already created that directory; it does not affect the result.

### E.8.3 — One Trap Hit and Fixed During the Self-Test

The wrapper Makefile's `build` target was originally written as `$(MAKE) …` (without `-f Makefile.mpss`). Because the wrapper file is itself named `Makefile`, that command reads it again, and so **recurses forever**: during the self-test it recursed all the way to `make[7]`, the log grew to 420,000 lines and 31 MB, and the machine ran out of memory. The fix is that every invocation passes an explicit `-f Makefile.mpss` (or `-C subdir`). This is recorded in a comment in `08-mic-module/Makefile` as a release caveat.

### E.8.4 — A Second Wrapper-Layer Bug Exposed by a Real Installation: Do Not Put `/usr/include` into `C_INCLUDE_PATH`

Once the recursion trap of E.8.3 was fixed, per-package `make install` passed completely under a **staged installation** (`DESTDIR=/tmp/…`), but when switched to a **real installation** (`sudo make install`, `PREFIX=/usr`), `04-mpss-micmgmt` failed while compiling its first C++ file:

```text
C_INCLUDE_PATH=/usr/include ... g++ ... -c src/mic_device.cpp
/usr/lib/gcc/loongarch64-aosc-linux-gnu/15/include/c++/cstdlib:83:15:
    fatal error: stdlib.h: No such file or directory
   83 | #include_next <stdlib.h>
```

The cause is that the wrapper Makefile unconditionally puts `$(DESTDIR)$(PREFIX)/include` into `C_INCLUDE_PATH`; in a real installation that expands to `/usr/include`, which is a system directory the compiler already has, and once it appears a second time, the `#include_next <stdlib.h>` line in libstdc++'s `<cstdlib>` (meaning "keep searching after the current directory") skips the real `stdlib.h`. A staged installation does not expose this, because `<stage>/usr/include` contains only the few headers we install ourselves and no `stdlib.h`.

The fix: only pass the search path explicitly when `DESTDIR` is non-empty or `PREFIX` is not `/usr`; all four wrapper Makefiles — `03-mpss-daemon`, `04-mpss-micmgmt`, `06-mpss-coi`, `07-mpss-myo` — do so. After the fix, `make build PREFIX=/usr` passes for all four packages, and staged installation still works.

This also highlights an operational point: **a direct `sudo make install` performs the build as root**, leaving root-owned object files in the source tree, after which rebuilding as an ordinary user fails with `can't create objs/xxx.o: Permission denied`. The recommendation is to `make` as an ordinary user first and then `sudo make install`; both READMEs say so, and if it has already happened, `sudo make clean` or `sudo chown -R $USER .` restores the tree.

### E.7.5 — Using `micctrl --hostkeys`, and One Two-Sided Inconsistency

The semantics of this option are stated clearly in the source (the comment at `micctrl/network.c:157` and the help text at `:164`):

```text
micctrl [global options] --hostkeys=<dir> [sub options] <Xeon Phi card>
The --hostkeys copies the ssh host keys from the specified directory to the Xeon
Phi file systems /etc/ssh directory. ... There is not coresponding micctrl option
to save the keys.
```

Three things are easy to trip over:

1. **The argument must be attached with `=`.** The option is declared as `optional_argument` at `micctrl.c:83`, so writing `--hostkeys <dir>` makes the directory be parsed as a **device name** and reports `Error: Invalid device name`; only `--hostkeys=<dir>` treats the directory as the argument.
2. **It requires real root.** It checks `getuid()` (not `geteuid()`), so even with the setuid bit installed on `micctrl`, an ordinary user running it gets `[Error] Only root is allowed to use this option`.
3. **The direction is "host → card", and there is no reverse option.** It copies the card-side host keys from the directory into the MicDir's `etc/ssh`, replacing the set that `--initdefaults` generated at random (so that every rebuild of the card presents the same host keys); to go the other way and collect the card's keys into `known_hosts`, you have to fetch them yourself from `/var/mpss/mic0/etc/ssh/*.pub`.

There is also a **two-sided inconsistency exposed by patch 19**: `--hostkeys` only recognizes the file names listed in `hostkeynames[]` (`network.c:873`), and at the time that table still held `dsa` and the protocol 1 `ssh_host_key`, which no longer matched the generating side that had been changed to `ed25519`/`rsa`/`ecdsa` — the result being that ed25519 keys in the directory were silently ignored and the count could never reach `LEN_KEYNAMES`, printing `Warning - only found 4 of normal 8 files` every time. After patch 21 brought the table into sync with 6 modern names, `Host ssh files copied from <dir>` is printed only when all six files are present.
