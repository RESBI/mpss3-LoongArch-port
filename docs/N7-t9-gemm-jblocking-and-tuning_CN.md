# 附录 N7 — T9 GEMM 步骤 5：j 分块与寄存器块调参

**实测效果：FP32 149.2 → 260.9 GFLOPS，FP64 68.1 → 133.9 GFLOPS**
（N=2048，244 线程；三次取最好）。两项彼此独立的改动，都是靠参数扫描而非推理
找到的 —— 这本身就是本节的教训。

## 1. 剩下的流量

走完 [N6](N6-t9-gemm-row-stride-padding_CN.md) 之后单核问题解决了，
下一个限制表现为跨核扩展不完美。把流量算清楚就明白了：
微内核为它处理的**每一个** j 条带都要把 `MR` 行 A **完整**重读一遍：

```
A 流量 = njs × (N/MR) × (MR × N × 4 字节)
       = 128 × 256 × (8 × 2048 × 4)
       ≈ 2.16 GB          N = 2048，MR = 8
```

而 B 在打包后（[N5](N5-t9-gemm-b-panel-packing_CN.md)）只有约 16 MB。
A 就是全部的访存故事，它被重读了 128 次 —— 每个 j 条带一次。

## 2. 改动 A：一趟处理多个 j 条带

把内层嵌套反过来：固定 `i0`，先扫过连续 `jsb` 个 j 条带，再换下一个 `i0`。
A 的行就能在这 `jsb` 个条带之间驻留于 L1/L2，A 流量除以 `jsb`：

```c
#pragma omp parallel for collapse(2) schedule(static) reduction(+:t)
for (uint32_t jb = 0; jb < njsb; jb++)            /* njsb = njs / jsb */
    for (uint32_t i0 = 0; i0 < N; i0 += MR32) {
        const uint32_t js0 = jb * jsb;
        for (uint32_t js = js0; js < js0 + jsb; js++) {
            micro32p(A, lda, Bp, N, C, N, i0, js);
            t++;
        }
    }
```

并行任务数仍是 `(njs/jsb) × (N/MR)`，`jsb=32` 时 N=2048 有 1024 个任务，
对 244 线程足够。

**这个循环形状在 KNC 上必须满足两个约束：**

- **不能用 `min()`，不能用三元。** 内层上界最自然的写法是
  `js1 = (js0 + jsb < njs) ? js0 + jsb : njs`，而这是致命的：它编译成
  `cmova`，k1om 汇编器直接拒绝
  （[N2 约束 4](N2-t9-gemm-isa-constraints_CN.md)）。所以上界写成
  `js0 + jsb` 且不加夹取，安全性来自整除性 —— `pick_jsb()` 只会返回
  能整除 `njs` 的值。
- **`jsb` 必须随 N 自适应。** 一个能整除 2048 的固定 `jsb` 不能整除 256，
  内核在小 N 下就会拒绝运行。`pick_jsb()` 取满足下列条件的最大 2 的幂：
  整除 `njs`、且仍切出**至少四个** j 块、且任务数不少于 128：

```c
static uint32_t pick_jsb(uint32_t N, uint32_t NR, uint32_t maxjsb, uint32_t MR)
{
    const uint32_t njs = N / NR;
    for (uint32_t j = maxjsb; j > 1; j >>= 1) {
        if ((njs % j) != 0) continue;
        if ((njs / j) < 4) continue;
        if ((N / MR) * (njs / j) < 128) continue;
        return j;
    }
    return 1;
}
```

  "至少四个 j 块"这条下限是测量之后才加的：只切两块时，N=1024 产生 256 个任务
  给 244 线程 —— 正好一个波次，末尾波次不均的代价超过多出来的 A 复用收益。
  在该规模下这一条约值 2 倍。

## 3. 改动 B：把寄存器块**改小**

这是反直觉的结果。标准论证说 `MR` 越大越好，因为 B 每个 k 步载入一次、
被复用 `MR` 次，于是每 FLOP 字节数按 `(MR·4 + 64) / (MR·32)` 下降。扫描说不是：

| JSB32 | MR32 | JSB64 | MR64 | FP32 | FP64 |
|---|---|---|---|---|---|
| 32 | 8 | 16 | 4 | **260.9** | **133.9** |
| 32 | 8 | 8 | 4 | 236.3 | 130.7 |
| 32 | 8 | 8 | 8 | 221.9 | **70.3** |
| 32 | 4 | 8 | 4 | 227.1 | 129.5 |
| 16 | 8 | 8 | 4 | 223.4 | 130.6 |
| 8 | 8 | 8 | 4 | 206.1 | 133.4 |
| 32 | 16 | 4 | 8 | 183.9 | 69.6 |

`MR64 = 8` 对 `MR64 = 4` 最刺眼：**70.3 对 133.9 GFLOPS**，1.9 倍，
而这还是个**降低**运算强度的改动。原因在
[N3](N3-t9-gemm-explicit-vectorisation_CN.md) 的反汇编里就能看到：
`MR32 = 8` 时循环每次迭代已经从栈上重载五个 A 行指针，寄存器文件已到边。
再压上 8 个 FP64 累加器（外加广播、B 向量与地址寄存器）就溢出，
而在顺序核上溢出的代价远高于它换来的 B 复用。

解读：**在这个块尺寸下，KNC 的约束是寄存器文件，不是运算强度。**
出厂默认是 `JSB32=32, MR32=8, JSB64=16, MR64=4`；四个都可用 `-D` 覆盖，
以便在别的硬件上重跑这次扫描。

另外注意 `MR64 = 3` 返回 FP64 = 0 而不是错误答案：2048 不能被 3 整除，
`GemmVecRun` 里的校验直接拒掉该配置，而不是算出垃圾值。
这就是 §2 那条整除契约在起作用。

## 4. 结果

| | 步骤 4 | 步骤 5 |
|---|---|---|
| FP32，N=2048 | 149.2 | **260.9** |
| FP64，N=2048 | 68.1 | **133.9** |
| 占峰值 | 6.2% / 5.6% | **10.8% / 11.1%** |

两点值得注意。第一，FP64 是在这一步追平的：此前它停在峰值的 5.6%，
而 FP32 是 6.2%；之后两者都落在约 11%，也就是内核在两个精度上变得均衡。
第二，两半都不是预测出来的 —— j 分块是从流量账推出来的，
但 `MR` 效应的**大小乃至方向**都不是。那张扫描表花了一个下午，
是本系列里回报最高的产物。

## 5. 规则

> 当一个操作数要按另一个操作数的每个条带重读一遍时，把嵌套反过来、
> 一趟扫多个条带，流量除以扫描长度。要用运行时选取、以整除性保证安全的块尺寸，
> 并且不用 `min()` —— 在 KNC 上夹取是汇编错误，不是性能损失。
>
> 然后**扫描寄存器块，而不是论证它。** 教科书论证优化的是每 FLOP 字节数，
> 忽略了寄存器文件；在一个只有 32 个向量寄存器的顺序核上，
> 溢出每次都赢过运算强度。把 `MR64` 从 8 缩到 4，FP64 几乎翻倍。
