# 附录 M　可移植性与相容性评估（逐条对代码）

　　本附录回答三个问题，每一条都给出代码或实测出处，不用推测填空。核查对象是 `08-mic-module/patches/` 里的**改动全集**（10 个文件）。

| 问题 | 结论 |
|---|---|
| 1　宿主侧"非 4 KiB 页支持"的改动是否破坏与上游原版的行为相容性？ | **不破坏**。在 4 KiB 页宿主上，全部换算**退化为恒等**，线格式与算术与上游逐位相同；另有 3 处**有意**的行为差异，均为更安全的方向（M.2） |
| 2　现在能否在**各页大小**的 Linux 内核上编译、注册、传输？ | **可以**（4 / 16 / 64 KiB 均可）。核心是单段线上一页数**恒为 ≤512、与宿主页大小无关**（M.3.1）；前提是现代内核与卡端 512 段约束 |
| 3　加 LoongArch 支持是否破坏 x86／ARM 的编译？ | **不破坏**。补丁集中**没有任何架构相关代码**，LoongArch 只出现在注释里（M.4） |

## M.2　问题 1：与上游的行为相容性

### M.2.1　4 KiB 页宿主下"退化为恒等"的逐条证明

| 换算点 | 4 KiB 宿主（`PAGE_SIZE == 4096`）下的取值 | 与上游比较 |
|---|---|---|
| `SCIF_PEER_PAGE_FACTOR = PAGE_SIZE / SCIF_PROTO_PAGE_SIZE` | `4096 / 4096 = **1**` | — |
| `HOST_PAGES_TO_PEER(n) = n × factor` | `n` | **与上游直接打包页数逐位相同** |
| `PEER_PAGES_TO_LOCAL(n)` | 恒等（且本移植已无使用者） | 同上 |
| `micscif_get_dma_addr` 分支 1 的 `wpage`（`type == RMA_WINDOW_PEER ? 4096 : PAGE_SIZE`） | 两者都是 `4096` | **与上游的 `PAGE_SHIFT` 算术完全相同** |
| 分支 2 的 `num_pages[i] × wpage` | `× 4096` | 同上 |
| `micscif_map_window_pages` 打包 `RMA_SET_NR_PAGES(..., nr_pages)` | 宿主页数 | **这正是上游原版写法**（本移植的第一轮修复就是"改回上游写法"，见 I.12.1） |
| `prep_remote_window` 的重新打包循环（`HOST_PAGES_TO_PEER(num_pages[i+_m])`） | `num_pages[i+_m]` | **与上游的整段 `memcpy_toio` 结果相同** |

　　结论：**在 4 KiB 页宿主上，本移植的页大小机制是"透明的"**——所有因子为 1，线格式与地址算术与上游逐位一致。

### M.2.2　与页大小无关的改动及其相容性判定

| 改动 | 在 4 KiB 宿主上的效果 | 判定 |
|---|---|---|
| `struct reg_range_t` 等待队列指针化＋**等长填充** | 结构体**大小与各字段偏移不变**，每窗口多一次 `scif_zalloc` 与一次解引用 | **相容**。跨端安全：两侧只交换消息 payload（`ep`/`vaddr`/`phys_addr`/窗口令牌）与各自的地址数组，**从不交换整个窗口结构**；`regwq`/`unregwq`/`allocwq` 只在各自本地窗口上初始化与使用（卡端源码中 rma.c 4/2/3 处、nodeqp.c 4/2/1 处，均作用于本端结构） |
| `micscif_get_dma_addr` 找不到地址时 `BUG_ON(1)` → `return RMA_ERROR_CODE` | 上游会 panic 的情形改为返回错误 | **有意差异（更安全）**。上游从未走到这条返回路径（它先 panic），因此不损失任何"上游能处理而我们不能"的场景 |
| DMA 边界校验 `micscif_window_desc_valid()` | 描述不完整时返回 `-EINVAL`，不再启动 DMA | **有意差异（更安全）**。只在"上游会 panic"的输入上拒绝；实测 T4（15/0）与 T8 三档（各 12/12）无误报 |
| `scif_register` 的 12 位页数守卫 | 单段 >4095 页时拒绝 | **实测永不触发**：单段线上一页数恒 ≤512（见 M.3.1），在上游与移植版上都是恒等操作 |
| 诊断探针（`MIC scif …`）与 `mic_dbg()` 开关 | 默认 `pr_debug`（静默）；异常路径的 `DESC-*` 为常开 `printk` | **相容**。探针是移植新增，不替换任何上游输出；异常路径只在真出问题时打印 |
| 内核 API 迁移（`dma_mapping_error`／`pde_data`／`proc_ops`／`mmap_lock`／`vm_flags_set`／`get_user_pages` 仅 flags） | 在等价语义的新 API 上调用 | **相容（版本维度）**，见 M.3.3 |
| 补齐 `deploy`/权限/构建卫生等非模块改动 | 与本问题无关 | — |

### M.2.3　三处有意的行为差异（明确列出）

1. **坏描述不再 panic**，而是返回 `EINVAL`（实测：同一输入从"`BUG`＋进程 `D` 状态＋必须重启"变成"一次可诊断的失败"，机器照常可用）；
2. **上游的 `RMA_ERROR_CODE` 死代码被激活**：`micscif_rma_dma.c` 里 10 处判读现在真正生效（在 4 KiB 宿主上同样生效——这是行为差异，方向是更安全）；
3. **`scif_register` 多了一层拒绝条件**（12 位守卫），在现有分段规则下恒不触发，属纯防御。

## M.3　问题 2：各页大小内核上的编译与运行

### M.3.1　关键不变量：单段线上一页数与宿主页大小无关

　　段表的生成规则（`micscif_detect_large_page()`，`micscif_rma.h`）只有两种段：

- 普通页 → **1 页**；
- 大页 → 从当前位置**到下一个 2 MiB 边界**（`ALIGN(addr + 1, PMD_SIZE)`）。

　　于是送出到对端的页数（线上单位 4 KiB）为：

```text
普通段：1 × (PAGE_SIZE / 4096)          = PAGE_SIZE/4096
大页段：(2 MiB / PAGE_SIZE) × (PAGE_SIZE / 4096) = 2 MiB / 4096 = 512   ← 与 PAGE_SIZE 无关
```

| 宿主页大小 | `SCIF_PEER_PAGE_FACTOR` | 单段最大线上页数 | 是否触及 12 位上限（4095） |
|---|---|---|---|
| 4 KiB | 1 | 512 | 否 |
| 16 KiB（本机） | 4 | **512** | 否 |
| 64 KiB | 16 | **512** | 否 |

　　**所以 12 位字段在任何页大小下都不会成为限制**；这也解释了为什么那个守卫是纯防御性的。

### M.3.2　三档页大小的逐项检查

| 检查项 | 4 KiB | 16 KiB（实测） | 64 KiB |
|---|---|---|---|
| `addr` 对齐要求 | 宿主页（=4 KiB） | 宿主页（16 KiB），实测 4 KiB 对齐会 `EINVAL` | 宿主页（64 KiB） |
| `len` 对齐要求 | 4 KiB（协议页，等价） | 4 KiB（放宽自上游的"宿主页"，见 M.2.1 注） | 4 KiB |
| pin 长度 | `ALIGN(len, PAGE_SIZE)` | 同 | 同 |
| 单段线上页数 | ≤512 | ≤512 | ≤512 |
| **宿主方向**窗口段数上限 | 受 `prep_remote_window` 循环覆盖全部段（无 512 限制） | 同 | 同 |
| **卡端方向**窗口段数上限 | **≤512 段**（卡端代码只写第一页段表，实测，见附录 K） | 同 | 同 |
| 建议窗口大小 | ≤1 MiB（4 KiB 宿主 = 256 段） | ≤1 MiB（=64 段） | ≤1 MiB（=16 段） |

　　说明：卡端 512 段限制与**宿主页大小无关**（它是卡端 4 KiB 页的 `NR_PHYS_ADDR_IN_PAGE`）；因此在任何宿主上，卡端注册的大窗口都会失败，而宿主注册的大窗口在代码上不受该限制（现有 T8 CLI 把两侧窗口设为同一尺寸，这一点尚未单独实测，列为待验证项）。

### M.3.3　编译维度：抬高的是**最低内核版本**，不是架构要求

| 迁移点 | 所需内核 | 说明 |
|---|---|---|
| `get_user_pages()` 仅收 gup_flags | ≥ 4.9（完全去参在 5.x） | 旧内核需版本兼容层 |
| `proc_ops`、`pde_data()` | ≥ 5.6 | `file_operations`→`proc_ops` 迁移 |
| `mmap_lock`（替代 `mmap_sem`） | ≥ 5.8 | |
| `vm_flags_set()` | ≥ 6.3 | 旧内核写 `vma->vm_flags` |
| `dma_mapping_error()` | 长期存在 | 与架构无关 |

　　**结论**：移植版模块面向**现代内核**（本机 7.1.13 实测通过），在上述任一架构上都能编译；若要回到 MPSS 原本面向的 3.x/4.x 内核，需要给这几处加版本兼容宏（工作量小、尚未做）。

### M.3.4　小结论

**可以**在 4／16／64 KiB 页的现代 Linux 上编译、注册与传输，条件有三：① 内核版本满足 M.3.3；② 卡端注册的窗口段数 ≤512（附录 K 不变量）；③ 传输完成后显式同步（附录 L L.1）。

## M.4　问题 3：是否破坏其他架构的编译

### M.4.1　补丁集中的架构相关代码：**零**

对 10 个改动文件做全量扫描，`__loongarch__`／`CONFIG_LOONGARCH`／`__aarch64__`／`__arm__`／`__x86_64__`／`CONFIG_X86` 等宏**一次都没有出现**；`LoongArch` 一词只出现在 **4 处注释**（解释"为什么"要把等待队列指针化：该结构在 LoongArch 内核态无法模拟非对齐原子访问）。

### M.4.2　改动的性质（都对其他架构无害或更安全）

| 改动 | 对其他架构的影响 |
|---|---|
| 等待队列指针化＋等长填充 | 结构体大小/偏移不变；**修复的是"packed 结构里内嵌等待队列"这一跨架构隐患**，在 x86 上同样更安全（不影响行为） |
| 页大小算术（因子宏） | 4 KiB 上退化为恒等（M.2.1）；64 KiB 上满足不变量（M.3.1） |
| 内核 API 迁移 | 与架构无关，只与版本有关 |
| `BUG_ON`→错误返回、DMA 边界校验 | 在其他架构上同样是"更安全"的行为差异 |
| 诊断探针与 `MIC_DEBUG` 开关 | 纯新增，默认静默 |

### M.4.3　结论

**不破坏 x86／ARM 的编译**：没有引入任何架构条件编译、架构头文件或架构内联汇编。唯一的"门槛"是内核版本（M.3.3）。若要在旧内核上编译，需要版本兼容层；若要验证 x86/ARM 的**实际编译**，最直接的做法是在对应内核源码树上跑一次 `make -C <kernel> M=08-mic-module`（本仓库未做，因为手边只有 LoongArch 与卡端 k1om 两套树）。
