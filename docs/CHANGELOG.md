## 2026-10-06 — Settled: the chunk table transfers only one page (512 entries); Appendix K added; I.12.6's twelve-bit claim disproved

- **Settled (measured)** A 32 MiB card window arrives with 527 chunks of which entries 512 to 526 have a **raw value of `0x0`** (read before the page counts are stripped, via `RAW-SCAN`/`RAW-HEAD`/`RAW-TAIL`) — the card **never wrote those entries** — and 512 is exactly `NR_PHYS_ADDR_IN_PAGE` on the card, whose pages are 4 KiB. The card runs an unpatched upstream module, and the host cannot reconstruct what was never sent.
- **Disproved** I.12.6's earlier argument that the twelve-bit wire page count (4095 pages) is the binding ceiling was **wrong**: the chunking rule (`micscif_detect_large_page`) makes a normal page its own chunk and lets a huge page run to the next 2 MiB boundary, so a chunk holds at most 512 pages and the twelve-bit field is never reached. The section has been rewritten with the process kept; the guard stays as defence in depth but is no longer presented as the cause.
- **Added** [Appendix K](K-offload-memory-rules.md) (and its Chinese twin): user-side constraints for offload memory movement — **at most 512 chunks per window** (the invariant), windows of 1 MiB or less (three sizes green as measured), slicing by window, 26496-byte RMAs, pinning subject to `RLIMIT_MEMLOCK`, plus the dmesg checks.

## 2026-10-08 — Appendix N added: getting vector code out of k1om, 0.33 → 261 GFLOPS

- **Added** [Appendix N](N1-t9-gemm-optimization-overview.md) and its Chinese twin: a **series of eight** stand-alone reports on the T9 GEMM optimisation, one per step, each with the hypothesis, the change, the measured delta and the transferable rule. Index: N1 overview/results, N2 the four hard constraints, N3–N7 the five optimisation steps, N8 remaining headroom.
- **Measured** On the 7120P at N=2048 with 244 threads: **FP32 147–261 GFLOPS, FP64 120–138 GFLOPS** (6–11 % of the 2416 / 1208 GFLOPS peaks), against the T9 scalar baseline's 0.33 and 38× the previous best. The ladder, each number from one controlled best-of-three sweep: 0.33 → 6.39 (tiling, still **not vectorised**) → 57.4 (explicit IMCI micro-kernel) → 104.1 (warm-up + `schedule(static)`) → 113.9 (B panel packing) → 149.2 (A row-stride padding) → 260.9 (j-blocking + tile tuning).
- **Added** Four constraints that block the obvious approaches, each traced to measured compiler behaviour or the *Phi ISA Reference Manual*: k1om **never auto-vectorises** at any `-O` level (`vfmadd` is 0 under `-march=knc`, which leaves `-mavx512f [disabled]`); intrinsics need `-mavx512f`, which retargets the file to generic AVX-512F so **any scalar FP** becomes xmm forms KNC has no registers for; the ISA lacks `vcvtdq2ps`, all 64-bit integer vector ops, **any unaligned vector access**, and **`cmov`** — so **`? :` is unusable**, since it becomes `cmova` and the assembler stops.
- **Corrected** [Appendix J](J-acceptance-tests.md)'s and `tests/README.md`'s conclusion *"a card-side sink can only be built with `-O0`"*, which was evidenced by T7's crash at `-O1`/`-O2`. The observation stands but the generalisation does not: the rule is about the **source**, not the flag — a file that keeps every floating-point operation inside a 512-bit intrinsic and contains no `? :` builds and runs correctly at `-O2 -mavx512f`. T7 keeps `-O0` because its source *is* scalar.
- **Added** The memory-layout finding that produced the largest single gain, and the one most likely to be missed: with N=2048 the A row stride is exactly 8192 = 2¹³ bytes, while a 32 KB / 8-way / 64 B L1 indexes sets with address bits 6–11 — so **all 16 A rows alias to one L1 set** and 8 ways cannot hold them. Padding the stride by 64 B spread them and tripled per-core throughput (5.40 → 16.34 GFLOPS on one core).
- **Added** A tuning table showing the counter-intuitive result that a **smaller register tile wins**: MR64 = 8 vs 4 is 70.3 vs 133.9 GFLOPS, because the accumulator set spills. Also the diagnostic that precedes it — a latency-bound kernel scales linearly from 1 thread to the hardware threads per core and then flattens, which is how the memory-layout problem was localised.
- **Cross-referenced** from `tests/README.md` §VIII, which is now a pointer to this series rather than an inline write-up; and from `tests/README_T9.md`, `tests/CHANGELOG_T9.md`, and the repository-root `T9_FINAL_REPORT.md`.

## 2026-10-08 (addendum) — Appendix N second sub-series: T7 N-body, 2.7 → 52.4 GFLOPS

- **Added** [N9](N9-t7-nbody-overview.md)–[N12](N12-t7-nbody-headroom.md) and their Chinese twins: optimising T7's N-body integrator. Five runs per tier on the 7120P, quoted as min / median / max because the spread is large: tier 1 (N=1024) 0.52 → 0.79 / **2.01** / 2.84 GFLOPS; tier 2 (N=8192) 2.12 → 20.3 / **29.0** / 30.7; tier 3 (N=16384) 2.70 → 41.3 / **51.6** / 54.5. Best single observation anywhere: 56.2 GFLOPS. So the honest headline is **15×–21×**, median ≈19×, and tier 3's median is 4.3 % of the card's ≈1208 GFLOPS FP64 peak, up from 0.22 %.
- **Correctness is unchanged**: the tier-1 checksum, which the host reference must match to 1e-9 relative, agrees **bit for bit (0.000e+00)** on a 20-step integration of a chaotic system — with the reciprocal-square-root replaced by an entirely different algorithm. The reason is a design choice worth carrying forward: vectorising **over `i`** with `j` broadcast keeps each body's `j` accumulation in the same order and with the same roundings as the scalar reference, so the only arithmetic that differs is `1/sqrt` itself. Vectorising over `j` would have reduced across lanes and made a bit-exact match impossible in principle.
- **Found (ISA manual)** KNC's FP64 pipeline has **no square root, no divide, no reciprocal and no reciprocal-square-root** — the manual's PD-suffixed instruction index contains `VADDPD`/`VSUBPD`/`VMULPD`/`VFMADD*PD`/`VCMPPD`/`VMOVAPD`/`VGETEXPPD`/`VGETMANTPD` and nothing else of that kind. The FP32 side does have them (`VRSQRT23PS`, `VRCP23PS`, `VEXP223PS`). `sqrt()` and `/` on a double therefore compile to library calls costing ~285 cycles per particle pair — which was the entire cause of T7's 2.7 GFLOPS.
- **Added** A construction for a 1-ulp FP64 `1/sqrt(x)` out of what does exist: split `x = m·2^e`; handle `q^e` with four branchless masked scaling steps driven by value comparisons (there is no usable double→int conversion); fit `m^(-1/2)` with a degree-5 minimax polynomial (1.17e-5, verified independently on a 10⁶-point grid); two Newton iterations take it to 6.2e-20. ~30 vector instructions per 8 values.
- **Found (hardware)** `VCMPPD` on KNC uses only `IMM8[2:0]` — the manual's table has eq/lt/le/unord/neq/nlt/nle/ord and instructs callers to "swap operands, use LE" for `ge`. GCC encodes `_CMP_GE_OS` as immediate 13, the AVX-512 form, which the hardware reports as an invalid opcode. Writing `_mm512_cmp_pd_mask(threshold, k, _CMP_LE_OS)` instead fixes it. **This is a general hazard**: the assembler catches instructions KNC lacks outright, but not instructions whose *immediate encoding* differs.
- **Found (hardware)** `calloc`'s 16-byte alignment is not enough: `vmovapd` requires 64 and KNC has no unaligned vector access, so the first vectorised build died with a general-protection fault. All arrays passed to the vector kernel now use `posix_memalign(..., 64)`.
- **Explained** The `vpackstorelpd` crash that has pinned T7 to `-O0` all along, now with the addressing form identified: the working `-O0` build has 12 of them, all `%rbp`-relative; the crashing `-O2` build has 11, of which one is `0x10(%r12)` — a single-double store using KNC's compressed `disp8*N` form, which the manual flags as element-granular for `VPACKSTORE`. The count really is not the criterion. The way out is not to fix the instruction but to stop generating it, which the vector kernel does (zero of them) by returning results as full-width aligned `_mm512_store_pd`.
- **Added** The architecture that makes this work: the card-side sink is now **two translation units with different optimisation levels** — `nbody_vec.cpp` at `-O2 -mavx512f` (all the vector math) and `nbody_sink.cpp` at `-O0` (the `sin`/`cos` initial conditions, kinetic energy, checksum, timing) — linked into one sink, with an interface that carries pointers and ints and never a `double`.
- **Added** The measurement that localises the remaining 95 %: the inner loop is 41 instructions per 8 pairs and takes ≈230 cycles, i.e. 5.6 cycles per instruction. `-O2`/`-O3`/`-O3 -funroll-loops` are flat (52.02/51.34/48.63), so it is not codegen; it is an in-order core paying a ~15–20-deep dependent chain serially. Next step recorded: unroll over `i` so two independent chains are available to the scheduler, which doubles the ILP without changing the summation order.

## 2026-10-08 (second addendum) — T7 round two: i-unroll, prefetch, and four ablations

- **Added** Two `i` blocks per `j` iteration in `nbody_accel`, plus `VPREFETCH0` on the four load streams. Measured tier 3, best-of-N: 52.4 (baseline) → 54.5 (unroll) → **56.2** (unroll + prefetch at distance 16). Small gains, and honestly reported as such.
- **Found** The earlier prediction in N12 — that overlapping two independent reciprocal-square-root chains would approach 2× — was **wrong**; it gave 4 %. The disassembly suggests register pressure ate it: 17 constant vectors are hoisted into `zmm`, and the 2-block loop contains 83 `vmovapd` against 57 for the 1-block loop. Recorded as a wrong prediction rather than quietly revised.
- **Found** The unroll introduced a real bug that only the tier-1 numbers revealed: processing two blocks per iteration halves the parallel work items, and N=1024 has just 64 groups against 240 threads, so over half the machine idled (tier 1 fell 2.86 → 0.72–0.97). The kernel now falls back to one block per iteration when the items cannot fill the threads; tier 1 recovered to a median 2.01.
- **Found** The guard itself cannot be written the obvious way: `if (c) x = 0;` becomes `cmovb` and the assembler stops with ``Error: `cmovb' is not supported on `k1om'``. Written as a comparison result multiplied in (`nvp *= (unsigned)(nvp >= 4u * nthreads)`), which yields `setae`. The `cmov` constraint of [N2](N2-t9-gemm-isa-constraints.md) hit again, from an unexpected direction — at runtime, in integer code that has nothing to do with the vector kernel.
- **Found (negative result)** `_mm_prefetch` and `__builtin_prefetch` do not work on k1om at all — ``Error: `prefetcht0' is not supported on `k1om'``. The manual's MVEX forms `VPREFETCH0/1/2/NTA` assemble only through inline assembly. A single-run distance sweep (0/4/8/16/32/64) showed nothing at all; only best-of-5 resolved the +2.3 %. Below ~5 % this card cannot be measured with single runs.
- **Added (measurement)** Two ablations that localise the remaining 95 %: replacing the four masked scaling steps with unmasked equivalents gives **54.4 → 64.6 GFLOPS (+19 %)**; removing the reciprocal-square-root entirely (`inv = m_j`) gives **108.1 GFLOPS (+96 %)**. So the transcendental chain is about half the runtime — but even a perfect one caps the kernel at 9 % of peak, because with it removed the surrounding 14-instruction loop still takes ≈111 cycles. **The floor is the loop's memory and issue behaviour, not the mathematics**, which inverts the priority N12 originally assumed.

## 2026-10-08 (third addendum) — T7: five tiers, and a verification that can fail

- **Added** Two larger tiers to T7 (N=32768 steps=4, N=65536 steps=2), with `NTIER` shared between the host and the driver script. They change the conclusion: the **full** vector kernel reaches **95.4 GFLOPS** (best observed 100.96) at N=65536 — 7.9 % of the card's FP64 peak — while the scalar `-O0` baseline is flat at ≈3 GFLOPS from tier 3 upward, because it is bound by software `sqrt` and division whose per-pair cost does not depend on problem size. The honest speedup is **8.0× / 18.3× / 21.0× / 26.6× / 31.6×** across the five tiers, measured on identical initial conditions with both builds passing the reference check.
- **Found (serious)** T7's checksum comparison **could not detect a wrong force law**. Deliberately setting `inv = 0` — deleting the gravitational force entirely — left the host-reference checksum passing (差 1.58e-14 against a 1e-9 threshold) and made the energy error *smaller* (1.19e-06 against 3.00e-05). Reasons: the dynamics were ballistically dominated, and the initial conditions were a regular lattice whose net force is symmetry-cancelled. See [N13](N13-t7-verification.md).
- **Added** Three independent verification layers to replace it. **Layer 1**: a 512-point log-uniform sweep of the card's `rsqrt_pd` against scalar `1/sqrt`, reported in `Result` — max relative error **2.556e-16**. **Layer 2**: the vector force kernel run on the first 64 bodies and compared against a scalar libm loop in the scalar translation unit on the card — max relative error **6.340e-16**. Re-running the four broken variants against layer 2 catches **all of them** (errors 1.000e+00 to 1.001e+00) where the checksum caught none. **Layer 3**: the host reference is now compared at **all five tiers** rather than only the smallest, parallelised **over `i` only** so each thread keeps a sequential `j` loop and the summation order stays comparable.
- **Changed** The initial conditions are now an integer hash (`hash01`) instead of a jittered lattice — irregular, so the force dominates the dynamics, and bit-reproducible across host and card (integer arithmetic plus one exact power-of-two multiply), which `sin`/`cos` are not. The suite now reports **17 checks**, all passing.
- **Found** The tier-3 ablations that this appendix previously relied on were contaminated by fixed overhead, and one of them was misleading in a specific and repeatable way: replacing the masked scaling steps with unmasked equivalents measured +37 %, but that transformation also leaves `k` dead, so the compiler deletes more than the four compares under study. **Ablation by semantic breakage measures the compiler's response to broken semantics, not the cost of the removed component.**
- **Added** The replacement that the +37 % pointed at — a degree-9 polynomial in the exponent, `P(e) ≈ 2^(-e/2)`, no compares and no masks — and measured it: **a wash**. `vcmp*` 20 → 0, but tier 4 82.34 vs 83.17 and tier 5 99.84 vs 98.81, both fully verified at 1-ulp accuracy (2.953e-16 vs 2.556e-16). Kept behind `-DNB_RSQRT_POLY=1` as a verified equivalent; the mask version stays the default.
- **Found (negative result)** Replacing the four scalar broadcasts with aligned 8-wide `_mm512_load_pd` is **slower** (92.7 vs 98.4 at tier 5). Broadcasts are not the bottleneck; a data-layout change to avoid them would buy nothing.
- **Added** `-DNB_SCALAR_BASELINE=1` to the card-side sink, so the scalar `-O0` implementation can be rebuilt and run on the same inputs as the vectorised one — the comparison in [N9](N9-t7-nbody-overview.md) §1 is apples-to-apples rather than historical.
- **Found** The `cmov` constraint of [N2](N2-t9-gemm-isa-constraints.md) was hit three more times: in the unroll guard (`cmovb`), in `nbody_rsqrt_probe` (signed `n / 8` → `cmovs`), and in the host's tier fallback. It is now the most frequently re-encountered trap in this codebase, and the workaround is always the same — write the condition as a comparison result multiplied in, never as a conditional assignment.

## 2026-10-08 (fourth addendum) — T7: a sixth tier, a four-step floor, and an opt-in reference

- **Added** Tier 6, N=131072 (7 arrays × 1 MB — 7 MB on the card, well past every cache level). Six tiers now: 1024 / 8192 / 16384 / 32768 / 65536 / 131072.
- **Changed** Every tier runs **at least 4 steps** (20/10/5/4/4/4). Shorter integrations gave the force too little time to separate the trajectory from the ballistic term, which is the weakness [N13](N13-t7-verification.md) §1 is about; a 4-step floor keeps the end-to-end check meaningful at the large tiers too.
- **Measured** The extended curve, scalar `-O0` vs vector on identical inputs: **0.52 → 2.38** (4.6×), **2.09 → 20.38** (9.8×), **2.65 → 56.48** (21.3×), **2.97 → 86.72** (29.2×), **3.02 → 105.05** (34.8×), **3.07 → 104.72** (34.1×). Two conclusions the three-tier version could not support: the scalar build is **flat at ≈3 GFLOPS** from tier 3 up (bound by software `sqrt`/division, whose per-pair cost is independent of N), and the vector build **saturates at N ≈ 65536** — tiers 5 and 6 land on the same number, 105.05 and 104.72, i.e. 8.7 % of the ≈1208 GFLOPS FP64 peak. Tier 6 exists to demonstrate the plateau, not to set a record.
- **Changed** The O(N²)·steps host reference is now **opt-in for large N**. Running it at all six tiers cost ~5.2 × 10¹⁰ pair evaluations at N=131072 and took the suite from **32 s to 227 s**. It now runs by default only for N ≤ 16384 (`NREF_DEFAULT`), forced everywhere by `T7_REF=1`, and the driver records a skipped tier as **SKIP, never PASS** — the point of [N13](N13-t7-verification.md) is precisely that a check which did not run is not evidence. Both modes verified: default 16 pass / 3 skip / 0 fail in 32 s; `T7_REF=1` 19 pass / 0 skip / 0 fail in 227 s.
- **Unchanged (deliberately)** The two kernel self-tests — force kernel vs scalar libm, `rsqrt` vs `1/sqrt` — are **not** gated and run at every tier. They are the layers with actual discriminating power and they cost milliseconds; only the expensive layer is optional.

## 2026-10-08 (fifth addendum) — T7: how much headroom is actually left

- **Found** An arithmetic error in this appendix's earlier headroom analysis: it divided the cycle budget by the wrong iteration count and concluded the kernel ran at 34 % of its issue bound. Corrected, the inner loop is **119 instructions, 78 of them FP-pipe ops, executed in 113–115 cycles — 1.05 IPC, 69 % of the FP-issue bound**, consistent at both N=65536 and N=131072.
- **Added (falsification)** The corrected model predicts that deleting the reciprocal-square-root (56 of 78 FP ops) should be worth ~3.5×. Measured at N=131072: **289.8 vs 109.7 GFLOPS — 2.6×**. The model holds; the shortfall is the 41 non-FP instructions.
- **Found (negative result)** A **manual lockstep** two-way `rsqrt` (`rsqrt_pd_2`), written because disassembly confirmed GCC does not interleave the two blocks' dependency chains, changed nothing: 106.8 / 110.0 vs 95.4–109.3. The premise was true but irrelevant — a kernel that is uniformly FP-issue bound has no stall for extra ILP to fill.
- **Found** The remaining lever is **algorithmic, not micro-optimistic**: Newton's third law halves the reciprocal-square-root count from n²/8 to n²/16 *and* reduces memory operations (four broadcasts per 16 pairs become one load per block pair). Expected **1.5–1.8×** — 160–190 GFLOPS, 13–16 % of peak. Not attempted: it changes the summation order, needs masked diagonal blocks and a load-modify-store on the partner accumulator. Recorded in [N12](N12-t7-nbody-headroom.md) §4 with the reasoning and the costs.
- **Found (verification gap)** The force-kernel self-test was **not testing the code that runs**. At 64 bodies the parallelism guard falls back to the single-block tail loop, so the two-block main loop — which computes essentially all of the physics — was never exercised; breaking *its* reciprocal-square-root left the self-test green. The kernel now exposes `nbody_accel_force2()`, the self-test runs both paths, and the broken two-block path is caught at 1.001e+00. See [N13](N13-t7-verification.md).

## 2026-10-08 (sixth addendum) — T7: every architecture-level knob is flat

- **Added (reference)** A KNC programming guide (*Phi Programming — KNC*, Atos, 2016) was added to the repository and extracted to `knc_prog.txt` for searching. Its architecture section supplies the fact that reframes the earlier micro-optimisation attempts.
- **Found (decisive)** **On KNC the instruction-level parallelism comes from the hardware threads, not from interleaving independent work inside one thread's instruction stream.** The guide states it directly: "at least 2 threads/core must be used to exploit ILP … an individual thread has the highest performance when running alone in a core". This is why the manual lockstep of [N12](N12-t7-nbody-headroom.md) §2 was pointless — the SMT scheduler already supplies the ILP, for free.
- **Measured (all flat)** Every architecture-level lever the guide identifies was swept at tier 6, best-of-3: **threads per core** 1/2/3/3.9/4 → 111.4–113.0 GFLOPS; **thread affinity** none / `GOMP_CPU_AFFINITY` spread over 61 or 244 / `OMP_PROC_BIND` spread, close, true → 110.7–113.1; **code alignment** (`-falign-loops` 16/32/64/128, `-falign-functions=64`) → 111.2–112.0; **prefetch hint** T0/T1/T2/NTA → 111.0–111.9. The thread-count result is the informative one: per-core throughput is identical whether one thread or four share the core, so a single thread already saturates the limit.
- **Found (toolchain-blocked)** KNC's MVEX **embedded broadcast** `{1to8}` — documented in the ISA manual and capable of folding all four `vbroadcastsd` in the inner loop into the arithmetic that consumes them — is unreachable: GCC never emits it (`_mm512_set1_pd(mem)` always becomes a separate `vbroadcastsd`), and GNU as rejects the syntax outright (``Error: junk `1to8' after expression``).
- **Confirmed (vendor documentation)** The manual's §4.3 states the mechanism behind the `vpackstorelpd` crash that [N11](N11-t7-two-units-and-three-traps.md) §4 had inferred from behaviour: a vector instruction's 8-bit displacement "is always multiplied by the total number of bytes of memory the instruction accesses … depending on any broadcast and/or data conversion in effect", and disp8*N "shrink[s] the required size of the paired-instruction decode window by 3 bytes". Same bytes, different effective address depending on operand form.
- **Bounded (memory)** The guide's measured GDDR5 bandwidth is 180 GB/s; T7's actual traffic at tier 6 is ≈21 GB/s, an order of magnitude below — consistent with the earlier finding that throughput is identical at N=8192 (fits L2) and N=131072 (does not).

## 2026-10-08 (seventh addendum) — T7: MPairs/s, the embedded broadcast, and why symmetry is blocked

- **Added** An **MPairs/s** rate to the sink, the host and the driver: million physics pairs `n(n−1)/2` per second, exactly 50 × the existing GFLOPS figure. Same pair count, different unit — no redefinition to hide behind. At tier 6 the sink reports ≈5.5 × 10³ MPairs/s.
- **Found (correcting the sixth addendum)** The MVEX **embedded broadcast `{1to8}` was not toolchain-blocked after all.** Standalone assembly accepts it (prefix byte `0x18` against `0x08`), and the reason inline asm failed is that **GCC's asm template eats bare braces** — it emitted `vmulpd (%rdi)1to8`. Written as `%{1to8%}` it works, and eight `{1to8}` instructions now appear in the compiled kernel with all four `vbroadcastsd` gone from the two-block loop. One constraint: the MVEX memory operand can only be Intel's last source, so `VSUBPD` yields `a − broadcast(*p)`; the needed `x[j] − x[i]` is recovered by switching the accumulation from `vfmadd` to `vfnmadd`, which is **bit-identical** (sign flip is exact and `fnmadd` is a single rounding of `−(a·b)+c`) — confirmed by the unchanged force self-test (6.340e-16) and checksum.
- **Measured (negative result)** The embedded broadcast is **6.5 % slower**: 5204.68 vs 5567.46 MPairs/s at tier 6, best-of-3, both correct. Longer encoding (extra prefix byte plus displacement) and different load-port behaviour are the likely reasons. Kept behind `NB_BCAST_FOLD`, default 0.
- **Corrected (N12 §4)** The earlier claim that symmetry is worth 1.5–1.8× was **wrong**. It counted the saved reciprocal-square-roots and never asked how the partner body's force gets back onto the right lanes. Symmetry is a scatter, a scatter needs a transpose, and **KNC has no lane shuffle of any kind**: `vpermilpd`, `vshufpd`, `vshuff64x2`, `vpermq`, `valignq`, `vshufi64x2` are all rejected, and the toolchain ships no `_MM_SWIZ_*` for the MVEX swizzle. The only cross-lane mechanism left is a memory round-trip costing ≈54 vector instructions per 64 pairs — against a saving of 28. Realistic landing zone **0.8–1.0×, i.e. no win**; the arithmetic is in N12 §4 as a table over j-tile widths.
- **Net** T7 remains at ≈105 GFLOPS / ≈5.3 × 10³ MPairs/s, and after this round the honest summary is: the kernel is at its FP-issue bound, every architecture-level knob is flat, the one documented ISA feature that was supposed to help makes it slower, and the one algorithmic lever left is forbidden by the ISA.

## 2026-10-08 (eighth addendum) — T7: the thread-count sweep was measuring nothing

- **Found (measurement bug)** The sixth addendum reported threads-per-core as flat. **It was not flat — the sweep never applied.** The host launches the card process with `COIProcessCreateFromFile`, and **the host environment does not cross that boundary**, so `OMP_NUM_THREADS=61/122/183/244` all ran the same 240-thread configuration. Checking the kernel's own reported thread count shows it at once: every setting reported **240**. Corrected by adding an `nthreads` field to `Params` (ABI updated both sides) fed from `T7_THREADS`, with `omp_set_num_threads()` called on the card before any parallel region. Verified: 61 → 61, 183 → 183, 244 → 244.
- **Measured (real sweep)** MPairs/s, best-of-7: tier 6 — 61 threads 2490.88, 122 → 4005.63, 183 → 4721.80, 220 → 5172.21, **240 → 5580.94**, 244 → 5001.22. Tier 3 — 220 is best at 3983.79, against 3502.82 at 240.
- **Two claims retracted.** (1) "A single thread already saturates the core" was an artefact of the broken sweep: SMT is worth **≈2.2×** here (2491 → 5581 going from 1 to 4 threads/core). (2) "Per-core throughput is the same at 1 and at 4 threads" likewise. The direct lockstep measurement in the fifth addendum is unaffected — it compared two builds at the same thread count — but its *explanation* no longer leans on the invalid sweep.
- **Found** **Over-subscribing is worse than leaving a core idle.** 244 threads — every hardware thread — is **10 % slower at tier 6 than 240** (four threads on 60 of 61 cores). The COI daemon and kernel work need somewhere to run. The library default already picks 240, so the shipped configuration is the right one.
- **Noted** `GOMP_CPU_AFFINITY` and `OMP_PROC_BIND` are host environment variables too, so the sixth addendum's "affinity is flat" reading is **not evidence of anything**. Affinity on the card is unmeasured and would need `sched_setaffinity` inside the sink.
- **Unchanged** The compile-time knobs were genuine measurements — they change emitted code, not the runtime environment. `-falign-loops` 16/32/64/128 and `vprefetch0/1/2/NTA` are flat (111.0–112.0 GFLOPS).
- **Added** `T7_THREADS=<n> bash t7_nbody.sh` as a supported knob.

## 2026-10-08 (ninth addendum) — N14: the N-body algorithm design specification

- **Added** [N14](N14-nbody-algorithm-design.md) and its Chinese twin — the N-body computation **design specification**, consolidating T7 into one document that is sufficient to re-implement or port the kernel. The optimisation history stays in N9–N13; N14 states only the conclusions that survived.
