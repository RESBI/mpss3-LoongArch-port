# 附录 N1 — T9 GEMM 优化：总览与结果

本系列共 8 篇，逐步记录验收测试 T9 的卡端 GEMM 如何从 **0.33 GFLOPS 提升到
147–261 GFLOPS**（Xeon Phi 7120P）。每篇覆盖一个步骤：假设、改动、实测效果、
以及可推广的规则。

- [N4](N4-t9-gemm-fixed-overhead_CN.md) — 步骤 2：消除固定并行开销
- [N5](N5-t9-gemm-b-panel-packing_CN.md) — 步骤 3：B 面板打包

- [N7](N7-t9-gemm-jblocking-and-tuning_CN.md) — 步骤 5：j 分块与寄存器块调参
- [N8](N8-t9-gemm-headroom_CN.md) — 剩余空间与下一个数量级

## 1. 为什么写这个系列

T9 最初的目的是证明 **COI offload 的计算正确性**，不是性能竞赛：朴素三重循环、
卡端 `-O0` 编译、0.33 GFLOPS。作为正确性测试这没问题，但作为性能数字是误导性的
—— 它只有该卡能力的 0.014%。

自然而然的下一个动作（"用 `-O2` 重新编译"）在这个工具链上不成立，而找出原因
走了几次弯路。结果是本测试套件此前积累了一条**过宽**的结论：*"卡端程序只能用
`-O0` 编译"*。下面这一系列把它替换成一条狭窄、可检查的规则：

> 约束不在优化档，而在源码里**有没有标量浮点，或有没有 `? :` 运算符**。
> 只要把所有浮点运算关进 512-bit intrinsic，`-O2 -mavx512f` 既正确，又比
> `-O0` 快 38 倍。

## 2. 结果

卡：Intel Xeon Phi 7120P，61 核 × 4 硬件线程，1.238 GHz。
按 61 核 × 1.238 GHz × 32 FLOP/周期计，峰值 **FP32 ≈ 2416 GFLOPS，FP64 ≈ 1208 GFLOPS**。

### 2.1 优化阶梯（N=2048，244 线程）

数字取自同一次受控扫描（每种配置跑三次取最好），因此**彼此可比**。跨时段
FP32 绝对值会波动至多 1.8 倍，见 §4。

| 步骤 | FP32 | FP64 | 改动 | 报告 |
|---|---|---|---|---|
| 朴素三重循环，`-O0` | 0.33 | 0.33 | — | — |
| 分块，`-O2 -march=knc` —— **完全未向量化** | 6.39 | 3.89 | 仅分块 | [N3](N3-t9-gemm-explicit-vectorisation_CN.md) |
| 1. 显式 IMCI 微内核 | 57.4 | 45.4 | 真正的 512-bit FMA | [N3](N3-t9-gemm-explicit-vectorisation_CN.md) |
| 2. 免计时预热轮 + `schedule(static)` | 104.1 | 61.1 | 去掉 ~0.15 s 固定开销 | [N4](N4-t9-gemm-fixed-overhead_CN.md) |
| 3. B 打包成 `[j条带][k][NR]` | 113.9 | 81.1 | B 不再在 16 MB 上跳步 | [N5](N5-t9-gemm-b-panel-packing_CN.md) |
| 4. A 行距加 64 B 填充 | 149.2 | 68.1 | **单项收益最大** | [N6](N6-t9-gemm-row-stride-padding_CN.md) |
| 5. j 分块 + 调寄存器块 | **260.9** | **133.9** | A 行跨条带复用 | [N7](N7-t9-gemm-jblocking-and-tuning_CN.md) |

### 2.2 最终状态

| | FP32 | FP64 |
|---|---|---|
| GFLOPS（N=2048，244 线程） | 147–261 | 120–138 |
| 三次取最好 | 260.9 | 133.9 |
| 占峰值 | 6–11% | 10–11% |
| 相对 T9 基线（0.33） | 445–790× | 365–420× |
| 相对"只分块不向量化"（6.39 / 3.89） | 23–41× | 31–35× |

**单核**吞吐是判断核本身是否健全的量：**单核 16.34 GFLOPS FP32**（4 硬件线程），
单核峰值 39.6 GFLOPS，即 41%。单线程为 4.13 GFLOPS。

### 2.3 按规模

| N | FP32 | FP64 |
|---|---|---|
| 256 | 3.0–3.6 | 3.1–4.2 |
| 1024 | 39–55 | 28–88 |
| 2048 | 147–261 | 120–138 |

小 N 受**并行粒度**限制而非核效率：工作量按 N³ 下降而微内核个数只按 N² 下降，
N=256 时凑不满 244 线程。这是基准的性质，不是内核的性质。

## 3. 数字是怎么验的

性能数字一律与正确性检查同时给出，而且检查强于"有结果回来"：

1. **反汇编门禁。** 脚本只有在卡端二进制同时满足 `vfmadd > 0` **且
   `xmm/ymm` 操作数为 0** 时才判通过。KNC 没有 128/256-bit 寄存器，产物里
   出现一个 xmm 就意味着卡上必崩；而 `vfmadd == 0` 意味着它悄悄退回标量
   —— 那正是 6.39 GFLOPS 那一版"看起来优化过"却什么都没做的样子。
   当前产物实测：总指令 1199，`zmm` 80，`vfmadd` 12，`xmm/ymm` **0**。
2. **两个独立的宿主参考。** 卡端回传 C 全部元素和的 16 个向量车道（它做不了
   标量归约，那会生成非法指令 —— 见 N2）。宿主用恒等式
   `sum_ij C[i][j] = sum_i sum_k A[i][k] · rowsumB[k]` 在 `O(N²)` 内重算同一个
   标量，并在 N ≤ 512 时**额外**做一遍完整 `O(N³)` 以证明该恒等式本身没错。
   相对误差：FP32 ≈ 1e-4，FP64 = 0（逐位一致）。
3. **不退化的测试数据。** `A[i][k]` 与 `B[k][j]` 同时随**两个**下标变化。
   早先的模式只依赖扁平下标 `i*N+k`；由于 N 是 64 的倍数，那会使 A 的每一行
   完全相同，于是行索引写错或转置都能通过。现在的模式是
   `A[i][k] = 1 + ((k + 16·(i mod 4)) mod 64)/64`，B 用其逆向变体。

## 4. 先说清 caveat

- **FP32 运行间波动大** —— 同代码同参数跨时段可达 1.8 倍（147–261 GFLOPS）。
  请引用区间或脚本的三次取最好值；单次跑出的高值不构成稳定性证据。
  FP64 稳定得多（120–138）。
- **低端也要如实看待。** 147 GFLOPS 不是可以丢掉的离群点：它是 `t9_gemm_vec.sh`
  自己记录的，用的是与跑出 261 完全相同的那份构建和参数，只是宿主机当时在忙别的活。
  最终配置的 8 次独立运行分别落在 147、172、219、232、242、261 以及其间的两个值。
  如果这个内核的数字要用于决策，请在空闲机器上至少取三次最好值并注明；
  不要引用单次结果 —— 无论它偏高还是偏低。
- **可留存的结果是"步骤方向"，不是绝对值。** 五个步骤中的每一个，在每一次测量里
  都把数字朝同一个方向推；变的只是幅度。正因如此 N2–N7 里那些**规则**才值得
  带到别的程序上去 —— 这也是本系列要列出完整阶梯、而不只给一个最终数字的原因。
- **这些是 intrinsic 内核的数字，不是 BLAS 的数字。** 厂商调优过的 `dgemm`
  还会再快数倍。本系列要交付的是工具链配方与访存布局经验，这恰恰是此前缺的。
- **机器是共用的。** 测量在正常工作机上、卡空闲时进行，但未做绑核与频率控制。
  五个步骤的**方向**每次都复现；具体百分比不复现。

## 5. 复现

```bash
cd release/tests
bash t9_gemm_vec.sh                          # N=256/1024/2048，244 线程
TIERS='2048' THREADS=244 bash t9_gemm_vec.sh
MR32=16 JSB32=32 bash t9_gemm_vec.sh         # 扫单个参数
bash t9_gemm_bench.sh                        # 0.33 GFLOPS 基线，作对照
```

每档日志（含卡端冷/热计时）落在 `release/tests/logs/run-<时间戳>/T9V-*.log`。
