# 附录 N5 — T9 GEMM 步骤 3：B 面板打包

**实测效果：FP32 104.1 → 113.9 GFLOPS，FP64 61.1 → 81.1 GFLOPS**
（N=2048，244 线程；FP64 拿到 33%）。一次 O(N²) 的布局变换，计时前做一次。

## 1. 访存模式

微内核固定 B 的 `NR` 列条带、沿 k 向下走：

```c
__m512 b = _mm512_load_ps(B + (size_t)k * ldb + j0);   /* ldb = N */
```

N=2048 时就是每前进 **8192 字节**取一条 64 字节 line，共 N 次。每条 line 被完整
取回、也被完整用完 —— **利用率**无可挑剔。不好的地方在地址序列：

- **换页。** 本移植的卡端页是 4 KiB，B 的一行 8 KiB 跨两页，所以这次遍历
  **每两次 k 迭代就跨一次页边界**。N=2048 意味着每个微内核约 1024 次跨页，
  乘 32768 个微内核。
- **预取器被废掉。** 硬件预取器找的是顺序或小步长推进。一个 8192 字节、
  每 128 条 line 才碰一条的步长，对它来说和随机没有区别。
- **工作集散开。** 微内核需要的数据散布在整个 16 MB 的 B 上而不是集中在一处，
  这正是让上一条的 TLB 压力产生代价的原因。

## 2. 变换

把 B 从行主序 `[k][j]` 重排为 `[j条带][k][NR]`：

```
Bp[js * N * NR + k * NR + 0 .. NR-1]  =  B[k * N + js * NR .. +NR-1]
```

内层遍历变成 `Bp + k*NR` —— **连续的 64 字节步长**，每次 k 迭代取满一整条
cache line，地址线性前进。字节数相同、line 数相同、没有元素级置换。

值得明确说出来的是：**这里没有转置**。一个条带的 16 个 float 保持原序。
变换只改变各条带的 k 切片被排布的次序。这让它退化为对齐的 64 字节拷贝、
不需要 shuffle：

```c
static void pack32(const float * __restrict__ B, float * __restrict__ Bp, uint32_t N)
{
    const uint32_t njs = N / NR32;
    for (uint32_t js = 0; js < njs; js++) {
        float *dst = Pc + (size_t)js * N * NR32;
        const float *src = Bc + (size_t)js * NR32;
        for (uint32_t k = 0; k < N; k++)
            _mm512_store_ps(dst + (size_t)k * NR32,
                            _mm512_load_ps(src + (size_t)k * N));
    }
}
```

成本：N² 读、N² 写 —— N=2048 时 16 MB + 16 MB。按该卡 DRAM 速率是几毫秒，
对约 100 ms 的内核约占 3%。且只在计时区间外付一次。

## 3. 结果

| | 打包前 | 打包后 |
|---|---|---|
| FP32，N=2048 | 104.1 | **113.9** |
| FP64，N=2048 | 61.1 | **81.1** |
| FP64，N=1024 | 46.34 | **56.98** |

诚实的读法：**收益有限，不是突破。** 剩下的性能仍被
[N6](N6-t9-gemm-row-stride-padding_CN.md) 的 L1 冲突问题锁着，所以这一步拿到的
比上面的分析所暗示的要少。它被保留在本系列里，是因为它便宜、正确，
并且能防止 B 在 A 侧问题解决之后变成新瓶颈 —— 否则步骤 4 的测量会被 B 限住。

另一个次要好处体现在循环次序上。条带被排布成连续之后，
`schedule(static)` 把连续的 `i0` 块交给一个线程，就意味着多个线程在差不多同一
时刻读**同一条** B 条带，于是它从 DRAM 取一次、之后由各核私有 L2 服务。
这就是循环次序取 `(j条带, i0)` 而不是 `(i0, j条带)` 的原因 —— 见
[N7](N7-t9-gemm-jblocking-and-tuning_CN.md)，那一步在此基础上继续。

## 4. 规则

> 当内核沿某个下标遍历一个操作数、而该下标的步长是很大的 2 的幂时，
> 问题不在字节数，而在**地址序列**。一次性 O(N²) 的重排成
> `[外层][内层][向量]` 连续布局，只花内核的百分之几，却把遍历变成线性的 ——
> 而且因为它是纯粹的 64 字节块拷贝，既不需要 shuffle 也不需要非对齐访问，
> 这两样恰恰是 KNC 都没有的（[N2](N2-t9-gemm-isa-constraints_CN.md)）。
