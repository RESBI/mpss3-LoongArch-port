## 2026-10-06 — 设备打不开时不再当场退出（修复）

- **修复**　`scif_ok()` 原写作 `if exec 3<>"$scif_dev" 2>/dev/null; then`。`exec` 是 POSIX 特殊内建，**重定向失败会让整个 shell 退出**，于是设备权限不对时脚本当场死掉并抛出裸错误（`common.sh: line 307: /dev/mic/scif: Permission denied`），根本走不到「跳过并提示」。改为在子 shell 里试开，失败只返回 1。
- **新增**　`scif_hint()`：打不开设备时打印两条可照做的修法（`sudo bash tests/t1_install.sh`，或临时 `chmod`），`run_tests.sh` 的前置状态块与 T3–T7 都已接入。
- **修复**　`need_scif` 这个守卫**从未定义过**（T3/T4 一直在执行「命令未找到 → 当成缺库 → 跳过」），现补上定义：只有真的缺用户态 SCIF 库时才跳过。
- **修复**　T1 不再覆盖上游的 `50-udev-mic.rules`，改为写入 `55-mic-perms.rules`（按文件名顺序在后生效），已存在则跳过；并修正一处过期提示（`install.sh` → `t1_install.sh`）。

## 2026-10-06 — 新增 T8：大数据量传输（4 GiB / 两端 checksum / 带宽）

- **新增**　`t8_bigxfer.sh` 与配套的 `src/bigxfer_srv.c`（卡端）、`src/bigxfer_cli.c`（宿主）：默认把 **4 GiB** 数据送到卡上。卡端先 `malloc` 整块并逐页 touch（大空间分配失败当场暴露），再探测**最大可注册跨度**并暴露给宿主；宿主用确定性 PRNG 填满源缓冲并算一次 checksum，然后分块 `scif_writeto`，最后两端 checksum 逐位比对，并按传输耗时算出带宽。卡端注册不下整块时自动退化为滑动窗口模式（每块同步一次、卡端自己搬运），日志写明模式与跨度，因此不会把「只传了一部分」误报成全量。
- **新增**　判据共 12 项：卡端大块 malloc 成功、注册成功、传输覆盖全量、两端 checksum 一致、带宽已测出、卡端收尾正常、无非对齐与内核异常。规模由 `TEST_BIG`／`TEST_BIG_WINDOW` 覆盖，`--quick` 降到 256 MiB。
- **实测（关键发现）**　卡端 4 GiB `malloc` 与**整块注册**都可行（256 MiB 实测 0.03 s 注册完成、direct 模式）；但**一次 64 MiB 的 `scif_writeto` 会失败并把进程卡死**：宿主陷在 `micscif_unregister_all_windows`（`D` 状态），卡端同名进程 `kill -9` 也无效，此后宿主的 RMA 通路整体失效（T4 随之失败），只能 `sudo rmmod mic && sudo modprobe mic` 并重启卡恢复。因此单次 RMA 硬性夹紧到 1 MiB。
- **新增**　宿主侧缓冲按**实际页大小**（`sysconf(_SC_PAGESIZE)`，本机 16 KiB）对齐：4 KiB 对齐会让 `scif_register` 直接报 `EINVAL`。
- **变更**　`deploy_card_file` 部署前先 `rm -f` 目标文件：卡上同名程序仍在运行时覆盖写会报 `Text file busy`（ETXTBSY）；T8 另加「清进程 + 重试一次」。
- **变更**　客户端输出改为行缓冲并逐块打印进度；脚本不再用 `timeout` 等客户端（`D` 状态进程收不到信号，会把整个阶段拖死），改为后台运行 + 限时轮询。

## 2026-10-06 — T8 全绿：4 GiB 两端逐位一致，并借此查出两处驱动缺陷

- **新增**　T8 完成真机验证：三档规模全部通过（各 12 项判据）。64 MiB：链路侧 359.0 MB/s、端到端 103.8 MB/s；256 MiB：338.6／101.2 MB/s；**4096 MiB：325.9／98.8 MB/s，两端 checksum 逐位一致（`0x76ac888ab487e57b`）**；全程无内核异常、无卡死进程。
- **新增**　**逐窗口校验**：宿主对每个 1 MiB 窗口算一次 checksum 随消息发出，卡端收到后先比对、再搬运，任何差错都能落到「第几个窗口、什么偏移、两侧各是多少」；收尾再比整缓冲。这是"确保大数据量传输不出错"这条要求真正的抓手。
- **修复**　卡端**暂存区与窗口 0 的目的地重合**：窗口注册在大缓冲开头，后续每个窗口的入站数据都会覆盖窗口 0 刚放好的数据 —— 症状是「头 1 MiB 错、其余正确」。改为单独开一块暂存区注册窗口，每窗口都从暂存区拷入大缓冲。
- **修复**　卡端**整缓冲校验长度被错误夹紧**：`if (done == 0 || done > span) done = span;` 在窗口模式下把累计接收量夹回窗口大小，导致只校验了第一个窗口（宿主算全量、卡端算 1 MiB，checksum 必然不等）。上限改为请求总量 `total`。
- **变更**　卡端测例改用 `-O2 -fno-tree-vectorize` 编译（禁向量化以避开卡端崩溃先例；校验和循环是热点，`-O0` 时 4 GiB 要 33.4 s，改用后 18.3 s）。可用 `TEST_BIG_OPT` 覆盖。
- **变更**　同时报告**链路侧**（只统计 `scif_writeto`）与**端到端**两个带宽：前者是 PCIe 真实吞吐，后者含卡端逐窗口校验与搬运的等待。判据采用端到端数字，链路侧数字一并打印以便定位瓶颈。
- **更正**　**撤回**此前"单次 RMA 不得超过 26496 字节"的结论：那是撞在已损坏的 RMA 通路上（见 `tests/CHANGELOG` 同日条目与 `docs/I` I.12）。单次 RMA 的真实上限尚未标定，T8 目前沿用 T4 已验证的 26496 字节作为保守默认值。
- **新增**　客户端逐片进度打印（前 16 片 + 每 128 片）与卡端窗口进度打印（前 4 个 + 每 256 个），配合 `D` 状态检查（`stat`/`wchan`），使"卡住"能在日志里直接定位。

## 2026-10-06（补）— 带宽口径更正、静默构建复测与 12 位页数上限

- **更正**　此前记录的「4 GiB 链路侧 325.9 MB/s」是**测量假象**：当时驱动里的诊断打印（`pr_info`）就在 RMA 拷贝路径上，每个 26496 字节片段要打几十行日志，耗时被打印主导。诊断打印改成 `MIC_DEBUG` 构建开关后在同一硬件上重测（静默构建）：**端到端 118.3／123.7／119.3 MB/s，`scif_writeto` 内耗时带宽 2978.8／3835.3／3478.1 MB/s**，三档两端 checksum 仍逐位一致。
- **更正**　链路不是 x1 而是 **PCIe Gen2 ×8**（`lspci`：`LnkCap x16`、`LnkSta Width x8 (downgraded)`，约 4 GB/s 理论），3478 MB/s 正落在其实际能力区间；此前「与 x1 链路吻合」的说法作废。
- **结论**　凡与打印相关的耗时数字都必须在静默构建下重测。T8 的判据采用端到端数字（受卡端逐窗口校验与搬运制约），`scif_writeto` 内耗时只用于定位瓶颈。
- **新增**　「实测坑」增至六条，第 6 条：单个连续段页数不得超过 4095（线上 12 位字段，宿主 16 KiB 页时约 63 MiB、卡端 4 KiB 页时约 15 MiB），超限由 `scif_register` 直接 `-EINVAL`（详见 `docs/I` I.12.6）。

## 2026-10-07 — 单次 RMA 标定到 1 MiB；新增独立细粒度测试集 tests/extra；COI 分批机制定案

- **标定**　单次 `scif_writeto` 阶梯实测（窗口 1 MiB、总量 64 MiB）：26496 B → 64 KiB → 128 KiB → 256 KiB → 512 KiB → **1 MiB 全部 12/12、两端 checksum 一致、0 事故**。此前 26496 字节确为过度保守；受卡端 512 段窗口约束，修复前无法继续放大。已更新附录 L L.2.4 与 K K.2 第 3 条。
- **新增**　`tests/extra/`：与 `run_tests.sh` **分开**的细粒度用例集（`run_extra.sh` + x01 环境与不变量 / x02 窗口方向性 / x03 RMA 阶梯 / x04 内核审计），把附录 K、L 的规则变成可执行断言；x01 实测 8/8 通过。
- **定案（任务 4）**　COI 内部**确实分批**：控制消息走固定尺寸预注册空间并按尺寸分流；较大负载走"按尺寸档注册窗口 → `scif_writeto` → 等完成 → 双向握手"，需要时用信号页 + fence；多处 `scif_register` 会循环以覆盖多 DMA 通道。依据：`transport/scif_comm.cpp` 的流程注释原文与 `mechanism/dma/dma.cpp` 的注释。已写入附录 L L.3.1，并在附录 F 新增 F.9「约束清单」指回 K/L。
- **受阻**　卡端模块重建（任务 1）被**工具链**挡住：`modules_prepare` 编译 `kernel/bounds.c` 时 k1om gcc 5.1.1 **内部编译器错误（段错误）**，导致 `generated/bounds.h` 缺失，卡端 `micscif.ko` 无法产出。三条可行路径见附录 M M.5 与本条备注：① 调 `-O0`/去 flag 重试；② 从 MPSS 源码包或镜像中取预生成的 `bounds.h`；③ 换能稳定运行 k1om gcc 的环境。
